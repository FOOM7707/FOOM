🌲 품(FOOM) 백엔드 구조 다이어그램

Firestore 컬렉션 관계 구조 + 예약·결제 핵심 흐름(오버부킹 방지 로직 포함)

1. 데이터 구조 (컬렉션 관계도)

누가 무엇을 갖고, 어떤 컬렉션이 어떤 컬렉션을 참조하는지 한눈에 보는 구조도입니다.

읽는 법: 화살표는 "1개가 여러 개를 갖는다(1:N)" 방향입니다. 예) providerProfiles(공급자 1명) → programs(그가 등록한 여러 프로그램).
핵심 포인트: scheduleTemplates(반복규칙)는 사람이 직접 만들지 않고, 이 템플릿을 바탕으로 Cloud Function이 자동으로 schedules(실제 회차)를 미리 생성합니다.

2. 예약→결제 핵심 흐름 (오버부킹 방지 로직)

이번 설계에서 가장 공들인 부분 — "결제 안 하고 이탈한 사람 때문에 자리가 계속 잠기는 문제"와 "여러 명이 동시에 마지막 자리를 결제해버리는 문제"를 동시에 막는 흐름입니다.

💡 식당 예약으로 비유하면: 손님이 예약하면 일단 자리를 잡아두되(정원 -1), 10분 안에 결제(=도착 확인)를 안 하면 자동으로 자리를 풀어줍니다(정원 +1 복구). 결제가 두 번 중복 통보돼도 이미 처리된 예약이면 무시합니다(멱등 처리).

3. 스케줄 생성 흐름 (weekly 반복 → 실제 회차)

"매주 월요일 10시" 같은 반복 규칙이 실제 예약 가능한 날짜별 회차로 어떻게 바뀌는지 보여줍니다.
