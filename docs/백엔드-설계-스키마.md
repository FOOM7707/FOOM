## 1. 설계 원칙

- Firestore는 NoSQL 문서형 DB이므로 관계형 테이블처럼 정규화하지 않고, **자주 함께 조회되는 데이터는 한 문서에 묶고**, **자주 늘어나는 목록은 서브컬렉션**으로 분리했습니다.
- 모든 컬렉션에 `createdAt`, `updatedAt`(서버 타임스탬프) 필드를 기본으로 둡니다.
- 상태값은 전부 고정 문자열로 관리하고, 4번에 전체 목록을 정리했습니다.
- **돈이 걸린 데이터(payments, settlements, bookings 상태)는 클라이언트가 직접 쓰지 못하고 Cloud Functions를 통해서만 씁니다.**
- **동시성이 걸린 자원(정원)은 반드시 Firestore 트랜잭션으로 처리하고, 결제 미완료로 인한 정원 점유는 TTL로 자동 해제합니다.** (v2 신규 원칙)

### 2-2. `providerProfiles` (문서ID = uid) — v10 구조 분리

**분리한 이유:** Firestore 보안규칙은 **문서 단위로만 읽기 권한을 줄 수 있고, 필드 단위 읽기 제어가 불가능합니다.** 문서를 읽을 수 있으면 그 안의 모든 필드가 노출됩니다. v9까지는 공개해야 할 정보(이름·소개·평점)와 절대 공개하면 안 되는 정보(정산 계좌·경고 이력·제재 상태)가 한 문서에 섞여 있어서, 프로그램 상세 화면에 운영자 정보를 띄우려면 계좌번호까지 열어야 하는 구조였습니다. **공개도 비공개도 못 하는 상태**라 문서를 둘로 나눴습니다.

> **대안 비교:** 공개 정보를 `programs` 문서에 복사해두는 비정규화 방식도 검토했으나, 공급자가 프로필을 고칠 때마다 모든 프로그램 문서를 갱신하는 동기화 함수가 필요하고 데이터 불일치 위험이 생겨 채택하지 않았습니다. 지금 규모에서는 문서 분리가 단순하고 안전합니다.

**`targetAgeTags` 산출 기준 (v13 — 이 표가 없으면 구현자마다 다른 경계를 씁니다):**

| 태그 | 만 나이 구간 |
|---|---|
| `infant` | 0 ~ 6세 |
| `child` | 7 ~ 12세 |
| `teen` | 13 ~ 18세 |
| `adult` | 19 ~ 64세 |
| `senior` | 65세 이상 |

- 프로그램 구간 `[targetAgeMin, targetAgeMax]`와 태그 구간이 **한 살이라도 겹치면** 그 태그를 붙입니다(양끝 포함). 예: 만 3~6세 → `['infant']`, 만 5~10세 → `['infant','child']`.

> **(v13 정정) `difficulty`의 출처를 하나로 통일했습니다.** 원래 "`walkingDistanceM`이 있으면 서버 산출, 없으면 공급자 선택값"이라고 적었는데, 그러면 값의 출처가 둘이 되어 서로 어긋날 수 있습니다. 게다가 보안규칙 허용목록(6-1)에 `difficulty`가 없어 **공급자가 쓸 수도 없는 상태**였습니다. 필터 라벨을 이미 "쉬움 1km 이하 / 보통 1~3km / 어려움 3km 이상"으로 거리 기준으로 보여주고 있으므로(17-3), **거리 하나만 입력받고 난이도는 계산하는 쪽**으로 정리했습니다. 등록 화면에는 걷는 거리만 입력받고 "난이도가 자동으로 표시됩니다"라고 안내합니다.
- `targetAgeMin`이 null이면 0, `targetAgeMax`가 null이면 120으로 치환해 계산합니다.
- **둘 다 null인 경우에만 `['all']`이고, 이때 다른 태그는 붙이지 않습니다.** 반대로 `all`을 다른 태그와 함께 붙이면(예: 모든 프로그램에 `all` 추가) 연령 필터가 아무것도 걸러내지 못하는 무효 필터가 됩니다.
- 검색 판정식: `(선택한 태그 ∩ targetAgeTags) ≠ ∅ || 'all' ∈ targetAgeTags`
- **이 경계를 나중에 바꾸면 기존 문서의 태그는 자동으로 안 바뀝니다.** 태그는 저장된 사본이므로 전체 백필 배치가 필요합니다.

> **(v13) `open`(상시모집)은 `nextScheduleAt`/`lastScheduleAt`을 반드시 명시적 `null`로 기록합니다.** 필드를 아예 만들지 않으면 그 필드를 쓰는 인덱스에서 문서가 빠져 **검색에서 통째로 사라집니다**(Firestore는 인덱스에 쓰인 모든 필드에 값이 있는 문서만 색인합니다). null이어도 부등호 필터에는 걸리지 않으므로 상시모집은 별도 경로로 처리합니다 — 17-2.

> 날짜·장소·최소/최대 인원은 전부 공급자가 프로그램 등록 시점에 직접 입력하는 값입니다. 시스템은 입력값을 저장·검증(최소인원 미달 자동취소, 최대인원 초과 시 신청 차단)만 할 뿐 값 자체를 정하지 않습니다.

> **(v10) 승인 후 수정 정책:** 공급자의 클라이언트 직접 수정은 `draft` 상태에서만 허용합니다(6-1). `published` 이후 제목·설명·이미지·정원·장소 등 **심사 대상 내용**을 바꾸려면 `PATCH /programs/{id}`를 거쳐야 하고, 서버는 이때 `status`를 `pending_review`로 되돌려 재심사에 넘깁니다. 가격 변경도 동일합니다. 이렇게 하지 않으면 "심사 통과 후 내용을 통째로 갈아끼우는" 우회가 가능해집니다.

> **(v9) 대표 썸네일 규칙:** 목록 카드·홈 사진 카드에 쓰는 대표 이미지는 `imageUrls[0]`으로 고정합니다. 별도 `thumbnailUrl` 필드를 두지 않고 배열 첫 장을 대표로 보는 방식이며, 공급자가 등록 화면에서 순서를 바꿔 대표 이미지를 지정합니다(솜씨당의 "대표사진 3~10장, 첫 장이 썸네일" 관행과 동일). 홈 화면 자동 슬라이드는 채택하지 않습니다 — 9-7 참고.

> **(v5 보완) draft → pending_review 전환 경로:** 보안규칙(6번)상 소유자는 `status` 필드를 직접 못 건드립니다. 그런데 기존 API 목록(5번)에는 이 전환을 시키는 엔드포인트가 없었습니다 — **`POST /programs/{id}/submit-for-review`**(v5 신규, Cloud Function)를 통해서만 `draft→pending_review`로 넘어가도록 보완했습니다. 관리자 승인/반려(`pending_review→published/hidden`)는 기존과 동일하게 `POST /admin/programs/{id}/review`.

### 2-4. 스케줄 구조 (v2 전면 재설계 — 정원 공유 버그 수정)

**문제였던 것:** v1에서는 `weekly` 타입 스케줄 하나에 `weekday`+공용 `remainingSlots`를 뒀는데, 이러면 8/10(월)과 8/17(월) 예약자가 같은 정원 풀을 공유하게 되는 버그가 있었습니다. → **모든 확정 회차는 날짜를 가진 독립 문서로 인스턴스화합니다.**

#### `programs/{programId}/scheduleTemplates` (서브컬렉션 — `weekly` 반복 규칙 정의용, 신규)

| 필드 | 타입 | 설명 |
|---|---|---|
| weekday | number | 0~6 (일~토) |
| timeOfDay | string | "10:00" 등 |
| capacityPerOccurrence | number | 회차당 정원 |
| activeFrom / activeUntil | timestamp | 이 반복 규칙이 유효한 기간 |

→ Scheduled Cloud Function이 이 템플릿을 읽어 **롤링 윈도우(오늘부터 90일, v13 변경)**로 실제 회차 문서를 `schedules`에 미리 생성합니다.

> **(v13) 왜 8주에서 90일로 바꿨나:** 검색 화면의 캘린더가 이동할 수 있는 범위와 이 값이 같아야 합니다. 캘린더가 롤링 윈도우보다 먼 달을 보여주면 **회차가 실제로 없어서 0건이 나오는 게 정상인데 사용자는 고장으로 읽습니다.** 캘린더 상한과 이 값을 90일로 통일했습니다(17-2).

> **(v3) 쓰기 권한:** `scheduleTemplates`는 클라이언트가 직접 쓰지 못하고 `POST/PATCH /programs/{id}/schedule-templates`(5번 API) 전용으로만 수정합니다. 이유는 아래 "템플릿 수정 시 캐스케이딩 정책" 때문 — 클라이언트 직접 쓰기를 허용하면 이 정책을 우회하게 됩니다.

**템플릿 수정 시 캐스케이딩 정책 (v3 신규):** 공급자가 이미 미래 회차가 생성된 상태에서 `capacityPerOccurrence`나 `timeOfDay`를 수정하면:
- 이미 예약이 1건이라도 존재하는 `schedules` 문서는 건드리지 않음
- 예약이 0건인 미래 회차에만 변경사항을 배치 반영
- 이 로직은 `PATCH /programs/{id}/schedule-templates/{id}` Cloud Function 안에서 처리(클라이언트가 직접 `schedules`를 고치지 않음)

#### `programs/{programId}/schedules` (서브컬렉션 — 실제 예약 가능한 "회차" 단위, 전부 날짜 기반)

| 필드 | 타입 | 설명 |
|---|---|---|
| **programId** | string | **(v10 신규)** 상위 프로그램 ID를 문서에도 비정규화 저장. 서브컬렉션은 경로에만 부모 ID가 있어 collectionGroup 쿼리 결과에서 부모를 알 수 없고, 인덱스(7번)도 걸 수 없음 |
| **programStatus** | string | **(v10 신규)** 상위 `programs.status` 사본. collectionGroup 보안규칙이 상위 문서를 `get()` 할 수 없어(쿼리 규칙은 문서 자체 필드만 평가) 공개 여부를 이 필드로 판단. 프로그램 게시·숨김 시 서버가 하위 회차를 일괄 갱신 |
| type | string | `single` / `weekly` / `series` (상위 scheduleType과 동일값, 조회 편의) |
| recurringTemplateId | string \| null | `weekly`일 때 어느 scheduleTemplates에서 생성됐는지 참조 |

| endAt | timestamp \| null | |
| seriesIndex / seriesTotal | number \| null | `series`일 때 회차 번호 |
| remainingSlots | number | **이 회차 전용 정원** (다른 회차와 공유 안 됨) |
| **forceOpen** | boolean | **(v4 신규)** 최소인원 미달이어도 공급자가 수동으로 강행 개설했는지 여부. 기본값 false — true면 D-1 자동취소 대상에서 제외 |

> **`open`(상시모집)은 `schedules` 서브컬렉션을 쓰지 않습니다 (v4 확정).** 정원 개념이 없는 건별 협의 예약이기 때문입니다. 대신 `programs.availableFrom/availableUntil`(이용 가능기간)만 두고, 실제 날짜는 예약 건마다 `bookings.negotiatedDate`에 개별 기록합니다 — 상세는 2-5 참고.

**최소인원 미달 자동취소 (v4 신규 — `minCapacity` 필드 활용):**
- `scheduledFn: checkMinCapacity`가 매일 실행되며, **진행일 D-1**인 `schedules` 중 확정(`confirmed`) 예약 인원 합계가 해당 `programs.minCapacity` 미만이고 `forceOpen=false`인 회차를 찾아 자동취소 처리합니다.
- 자동취소 시 관련 `bookings.status='cancelled_by_provider'`, `cancelType='standard'`, `penaltyRate=0`(소비자 귀책이 아니므로 전액 환불)으로 처리하고 소비자에게 알림 발송합니다.
- 공급자가 최소인원 미달 상태에서도 강행 개설하고 싶으면 `PATCH /programs/{id}/schedules/{id}/force-open` 호출 → `forceOpen=true`로 전환, 이후 자동취소 대상에서 제외됩니다 (벤치마킹한 솜씨당의 "수동 강제개설 우회로"와 동일한 설계).

**예약 완료(`completed`) 전환 (v5 신규 — 기존에 빠져있던 트리거):**
- `single`/`weekly`/`series` 타입: `scheduledFn: markBookingsCompleted`가 매일 실행되며, `schedules.startAt`(또는 `endAt`, 있으면 우선) 기준으로 **행사 종료 후 1일이 지난 시점**의 `confirmed` 예약을 `completed`로 전환합니다. 이 값이 리뷰 작성 조건(2-8)과 정산 대상 판단(2-7) 기준이 됩니다.
- `open` 타입: 별도 스케줄 함수 불필요 — `POST /bookings/{id}/check-in` 호출로 `checkInAt`이 기록되는 즉시 `status='completed'`로 함께 전환됩니다 (체크인=서비스 제공 완료로 간주).

1. `POST /bookings` 호출 시 `status='pending_payment'`, `expiresAt=now()+10분` 설정 + `schedules.remainingSlots` 트랜잭션 차감 (`open` 타입은 정원이 없으므로 이 차감 단계 생략)
   - **(v12) 참가자 정보 검증도 이 단계에서 수행합니다** — `participants` 길이 = `headcount`, 아동 대상 프로그램이면 모든 참가자에 `age`가 있고 프로그램 대상연령 범위 안인지, `guardian`·`emergencyPhone`이 채워졌는지. 하나라도 어긋나면 예약을 만들지 않습니다(15-6)
2. 10분 내 결제 미완료 시 Scheduled Function이 `expired` 처리 + `remainingSlots` 복구
3. PG 웹훅 수신 시 `expiresAt` 경과 여부 확인 후 `confirmed`로 전환

**환불정책 로직 (v4 확정 — 진행일 기준 유지):**
- 7일 이상 전 취소 → 전액 환불 (penaltyRate=0)
- 1~6일 전 취소 → 50% 환불 (penaltyRate=0.5) — **v4에서 확정** (마이리얼트립·에어비앤비 체험 등 다수 체험형 플랫폼이 진행일 기준을 쓰는 관행과 일치)
- 당일 취소 → 환불 없음 (penaltyRate=1.0)
- `cancelType='exempt'` → 위 구간 무관하게 전액 환불. `exemptReason`(천재지변/본인 질병·사고/직계가족 상) 기록 필수
- **(v5 보완) `open` 타입 전용 — `negotiatedDate` 확정 전/후 구분:** 위 진행일 기준 로직은 `negotiatedDate`가 있어야 성립합니다. `negotiatedDate=null`(아직 채팅으로 날짜 협의 전) 상태에서 취소하면 특정 회차를 점유한 게 아니므로 **전액 환불(penaltyRate=0)**. `negotiatedDate` 확정 후에는 그 날짜를 "진행일"로 간주해 위와 동일한 7일/1~6일/당일 구간을 그대로 적용합니다.

**공급자 귀책 취소 시 (`cancelType='provider_canceled'`):** 소비자에게는 사유 무관 전액 환불(penaltyRate=0) + `private/profile.warningCount` 증가 및 `violations` 서브컬렉션에 기록 — 단 `exempt`(면제 사유) 처리된 건은 경고 대상에서 제외. 상세 단계는 2-2 참고.

|---|---|---|
| **문서ID** | string | **(v2 변경)** auto-id 대신 **`pgTransactionId`(paymentKey)를 그대로 사용** — 웹훅 중복 수신 시 멱등 처리 |
| bookingId / consumerId | string | |
| pgProvider | string | 고정값 `tosspayments` |
| amount | number | |
| platformFee | number | 거래액의 10% |
| ~~withholdingTax~~ | — | **(v2 삭제)** 원천징수는 거래 단위가 아니라 정산 단위(settlements)에서 계산 — 아래 참고 |
| status | string | `pending` / `paid` / `cancelled` / `partial_refunded` / `refunded` / `failed` |
| receiptUrl | string \| null | 카드매출전표/현금영수증 URL |
| paidAt | timestamp \| null | |
| refundedAmount | number | |
| createdAt / updatedAt | timestamp | |

**웹훅 멱등성 처리 (v2 신규 원칙):** 웹훅 수신 시 해당 `pgTransactionId` 문서가 이미 `status='paid'`면 즉시 200 OK 반환하고 로직 종료 (중복 처리 방지).

**결제 금액 위변조 검증 (v10 신규 — 필수):** 멱등 처리만으로는 막히지 않는 구멍이 있었습니다. 결제창 호출은 브라우저에서 일어나므로 **프론트엔드 JavaScript를 조작해 3만 5천 원짜리 프로그램을 100원으로 결제 요청할 수 있습니다.** 서버가 금액을 대조하지 않으면 그대로 `confirmed`가 찍힙니다.

따라서 `POST /payments/webhook`은 상태를 바꾸기 **전에** 반드시 다음을 검사합니다.

1. PG가 통보한 실결제액이 `bookings.totalAmount`와 **정확히 일치**하는가
2. `bookings.totalAmount`가 `bookings.unitPrice × bookings.headcount`와 일치하는가 (스냅샷 내부 무결성)
3. 해당 `bookingId`가 `pending_payment` 상태이고 `expiresAt`이 지나지 않았는가

> **⚠️ 라이브 가격(`programs.price`)과 대조하면 안 됩니다.** 스냅샷을 두는 이유가 예약 이후 가격이 바뀔 수 있기 때문인데, 현재 `programs.price`와 비교하면 **가격이 변경된 뒤 결제하는 정상 사용자가 공격자로 판정되어 결제가 취소됩니다.** 검증 기준은 항상 예약 시점에 고정된 `unitPrice`입니다. `unitPrice`는 `POST /bookings`에서 서버가 `programs.price`를 읽어 기록하며, 클라이언트가 보낸 값은 무시합니다.

하나라도 어긋나면 `confirmed`로 전환하지 않고 **즉시 결제 취소(PG 승인 취소) 후 `payments.status='failed'`로 기록하고 관리자에게 알립니다.** 금액 불일치는 단순 오류가 아니라 공격 시도일 가능성이 높으므로 로그를 남깁니다.

> 결제 요청 금액을 클라이언트가 보내지 않게 하는 것이 더 근본적인 방어입니다. `POST /payments/checkout`에서 **서버가 `bookings.totalAmount`를 읽어 결제 금액을 직접 확정**하고, 프론트는 결제창에 쓸 키만 받아가는 구조로 구현합니다.

### 2-13. `aggregates` (v13 신규 — 읽기 공개 / 쓰기 서버 전용)

화면을 그리는 데 필요하지만 매번 계산하면 읽기 비용이 큰 값을 미리 접어둔 문서들입니다. 컬렉션 전체가 파생 데이터이므로 **소실돼도 재계산으로 복구 가능**해야 합니다.

| 문서 | 내용 | 쓰는 곳 |
|---|---|---|
| `aggregates/searchIndex` | 게시 중 프로그램의 **필터·정렬 필드만 추린 사본 배열** + `computedAt` | `GET /programs/search`의 유일한 데이터 소스. **검색 요청당 읽기 1건**(17-1). 1건당 약 300B라 200건이면 60KB — 문서 상한 1MiB의 6% |
| `aggregates/scheduleCalendar` | `{ "2026-08-15": 12, "2026-08-16": 3, ... }` + `computedAt` — 오늘~+90일 각 날짜에 회차가 있는 프로그램 수 | 검색 화면 캘린더의 "회차 있는 날" 점. **읽기 1건으로 달력 전체가 칠해집니다**(17-5) |
| `aggregates/homeStats` | 등록 전문가 수·누적 프로그램 수·평균 평점 등 | 홈 화면 지표(13번 P2에 올라와 있던 항목 — 자리만 잡아둠) |

> **이 컬렉션에는 개인정보를 넣지 않습니다.** 읽기가 전체 공개이므로, 집계 과정에서 특정 개인이 역산되는 값(예: 예약자 수가 1인 날짜의 상세)은 담지 않습니다. `searchIndex`에는 **게시된 프로그램의 공개 필드만** 담습니다 — `reviewNote`(반려 사유)나 공급자 연락처가 섞이면 비공개 정보가 공개 문서로 새어 나갑니다.

> **갱신은 증분이 아니라 전체 재생성입니다(v13).** 프로그램마다 이 문서를 조금씩 고치는 방식은 **모든 프로그램이 한 문서를 두고 다투는 구조**라 쓰기 경합이 생기고, `increment` 방식은 재시도 시 값이 부풀어 되돌릴 수 없습니다. `rebuildSearchIndex` 배치 하나만 이 컬렉션에 씁니다 — 상세는 17-5.

### 2-14. `phoneIndex` (v14 신규 — 전화번호 유니크 인덱스 / 읽기·쓰기 전면 차단)

문서 ID가 **정규화한 E.164 번호 그 자체**입니다(`phoneIndex/+821012345678`).

| 필드 | 타입 | 설명 |
|---|---|---|
| uid | string | 이 번호를 먼저 선점한 계정 |
| createdAt | timestamp | |

**왜 별도 컬렉션인가.** Firestore에는 유니크 제약이 없고, **트랜잭션은 쿼리 결과를 잠그지 못합니다.** "이 번호를 가진 `users` 문서가 있나?"를 트랜잭션 안에서 조회해도 아직 없는 문서에는 잠금이 걸리지 않아, 동시에 들어온 두 요청이 나란히 통과합니다. 번호를 **문서 ID로 삼아 `create`로 선점**하는 방식만이 경합을 막습니다.

> **읽기를 관리자에게도 열지 않습니다.** 문서 ID가 곧 번호라, 읽기가 열리면 번호를 하나씩 찍어보는 것만으로 가입 여부를 알아낼 수 있습니다 — 목록 조회 권한도 필요 없는 단건 조회 열거입니다. 관리자에게 필요한 조회는 목적이 기록되는 서버 API를 통해서만 수행합니다.

> **선점 실패는 가입을 막지 않습니다(v14).** 이미 다른 계정이 쓰는 번호면 **기록만 하고 그대로 진행**하며, 그 계정의 `users.phone`은 비워 둡니다. 차단은 쿠폰·프로모션 발급 시점에서 판단합니다 — 가입이나 예약 단계에서 막으면, 번호가 첫 예약 화면에서 들어오는 카카오 사용자가 되돌아갈 곳 없이 멈춥니다.

> **탈퇴해도 이 문서를 지울지는 아직 정하지 않았습니다.** 지우면 탈퇴 후 재가입으로 쿠폰을 다시 받는 경로가 열리고, 남기면 개인정보 파기 의무(제21조)와 부딪힙니다. 쿠폰 기능을 실제로 만들 때 법무 판단과 함께 정합니다.

## 5. 핵심 API (Cloud Functions) 엔드포인트 목록

### 인증/사용자
- `POST /auth/signup`, `POST /auth/provider/apply`, `GET /users/me`
  - **(v15 확정) `GET /users/me`가 돌려주는 것:** `users` 본문의 공개 가능한 값(`uid`·`role`·`name`·`email`·`phone`·`profileImageUrl`·`status`·`authProvider`·`identityVerifiedAt`) + 공급자면 `provider` 블록(`displayName`·`verified`·`approvalStatus`·`approvalNote`) + `isAdmin`. **`private/identity`는 읽지 않고 정산 계좌도 넣지 않습니다.** 반려 사유(`approvalNote`)는 본인에게 보여줘야 재신청이 가능하므로 포함합니다. `isAdmin`은 Firestore의 `role`이 아니라 **토큰 클레임**이 기준입니다 — 보안규칙과 함수 진입부가 보는 값이 그쪽이라, 둘이 어긋나면 클레임이 맞습니다(12-3)
- **`POST /auth/identity/verify`** — **(v11 신규)** 본인확인 완료 후 인증 결과를 서버에서 검증하고 `users/{uid}/private/identity`에 기록, `users.identityVerifiedAt` 갱신. 같은 `ci`를 가진 다른 계정이 이미 있으면 중복 가입으로 거부합니다. **인증 결과를 클라이언트가 보낸 값 그대로 믿지 않고 반드시 서버에서 재조회해 확인합니다**(6-2와 같은 원칙)

### 프로그램
- `POST /programs`, `GET /programs`, `GET /programs/{id}`, `PATCH /programs/{id}`(가격/상태 변경은 서버 검증 필요)
  - **(v13) `POST /programs`는 draft를 만들 때 `price`·`capacity`·`minCapacity`·`rainAlternative`를 기본값으로 채워 넣습니다.** 보안규칙이 `get(키, 기본값)`으로 방어하고 있어 없어도 수정은 되지만, 필드가 뒤늦게 생기면 화면과 검색 파생값이 어긋납니다
- **`GET /programs/search`** — **(v13 신규)** 검색·필터·정렬 전용. 카테고리 다중선택·기간·대상연령·가격·지역·난이도·배리어프리·우천대체·정렬을 한 번에 받습니다. **필터를 클라이언트 Firestore 쿼리로 만들지 않는 이유와 캐시 전략은 17-1.** 로그인 불필요, 함수 안에서 `status=='published'`를 하드코딩(17-6)
- **`syncProgramScheduleDates(programId)`** — **(v13 신규, 내부 함수)** 하위 `schedules` 변경 시 **해당 프로그램 문서의** `scheduleDates`·`nextScheduleAt`·`lastScheduleAt`을 재계산. **회차를 만들거나 지우는 모든 경로가 이 함수만 호출합니다** — 갱신 지점이 흩어지면 "달력에 점은 있는데 예약이 안 되는" 불일치가 생깁니다(17-2). **집계 문서는 이 함수가 쓰지 않습니다**(쓰기 경합 — 아래 `rebuildSearchIndex` 참고)
- **`scheduledFn: rebuildSearchIndex`** — **(v13 신규)** 10분 주기. 게시 중 프로그램을 전량 읽어 `aggregates/searchIndex`와 `aggregates/scheduleCalendar`를 **통째로 다시 만듭니다.** 단일 라이터라 쓰기 경합이 없고, 증분이 아니라 전체 재생성이라 **몇 번 실행돼도 결과가 같습니다(멱등)**. 지난 날짜 정리도 여기서 함께 처리 — 상세는 17-1·17-5
  - **`POST /admin/aggregates/rebuild`** — 같은 로직의 수동 실행구. 2-13이 요구한 "소실 시 재계산 복구" 경로
- **`scheduledFn: recalcProgramStats`** — **(v13 신규)** 일 1회. `bookingCount30d`(최근 30일 확정 예약 수)를 **게시 중 전 프로그램에 대해** 재계산합니다. 예약이 0건인 프로그램도 0으로 덮어써야 합니다 — 예약이 있는 것만 순회하면 위조값이나 옛 값이 남습니다. `ratingAvg`/`ratingCount`도 이때 실제 `reviews`와 대조해 보정합니다
- **`POST /programs/{id}/schedule-templates`** — (v3 신규) `weekly` 반복 규칙 생성, 즉시 롤링 윈도우만큼 `schedules` 인스턴스 생성
- **`PATCH /programs/{id}/schedule-templates/{id}`** — (v3 신규) 템플릿 수정, 예약 0건인 미래 회차에만 캐스케이딩 반영
- **`PATCH /programs/{id}/schedules/{id}/force-open`** — (v4 신규) 최소인원 미달 상태에서 공급자가 강제 개설, `forceOpen=true` 전환
- **`POST /programs/{id}/submit-for-review`** — (v5 신규) 소유자가 `draft→pending_review` 전환. 보안규칙상 소유자는 `status`를 직접 못 쓰므로 이 서버 함수를 통해서만 가능
- **`PATCH /programs/{id}`** — **(v10 신규)** `draft`가 아닌 상태(`pending_review`/`published`/`hidden`)의 내용 수정 전용. 심사 대상 필드(제목·설명·이미지·정원·장소·가격)가 바뀌면 서버가 `status`를 `pending_review`로 되돌려 재심사에 넘깁니다. **반려(`hidden`)된 프로그램의 수정·재제출도 이 엔드포인트로 처리합니다** — 별도 `hidden→draft` 전환은 두지 않습니다

- `POST /bookings/{id}/cancel` — 환불정책+`cancelType`/`exemptReason`/`penaltyRate` 계산 후 환불 API 호출. `provider_canceled`면 `private/profile.warningCount` 증가 및 `violations` 기록도 함께 처리
- **`PATCH /bookings/{id}/negotiate`** — (v4 신규) `open` 타입 전용, 채팅 협의 후 `negotiatedDate` 확정
- **`POST /bookings/{id}/check-in`** — (v4 신규) `open` 타입 전용, 당일 앱 체크인 → `checkInAt` 기록(정산 트리거)
- **`scheduledFn: releaseExpiredHolds`** — (v2 신규) 10분 경과한 `pending_payment` 예약을 주기적으로 `expired` 처리 + 정원 복구
- **`scheduledFn: checkMinCapacity`** — (v4 신규) 매일 실행, D-1 기준 최소인원 미달 & `forceOpen=false`인 회차 자동취소 + 전액 환불 + 알림
- **`scheduledFn: markBookingsCompleted`** — (v5 신규) 매일 실행, 행사 종료(`schedules.startAt`/`endAt`) 후 1일 지난 `confirmed` 예약을 `completed`로 전환 (리뷰 작성·정산 대상 판단 기준)

### 리뷰/문의
- `POST /reviews` — **(v10 강화 / v13 추가: 같은 트랜잭션에서 `programs.ratingAvg`·`ratingCount`를 갱신합니다 — 갱신 주체가 없으면 평점순 정렬이 동작하지 않습니다)** 완료된 booking만 허용하되, 그 예약이 **호출자 본인의 것인지**와 리뷰의 `programId`/`providerId`가 예약 문서와 일치하는지까지 서버에서 검증. 클라이언트 직접 쓰기는 보안규칙에서 차단됨(6-1). `POST /inquiries`, `POST /inquiries/{id}/messages`
- **알림 트리거 추가 (v4 신규):** `inquiries/{id}/messages`에 새 메시지 생성 시 상대방(공급자↔소비자)에게 알림톡/SMS 발송 — 웹은 푸시 알림이 불가하므로 문의 답변 도착 여부를 알림톡으로 대체 통지

### 관리자/정산
- **`GET /admin/providers?status=pending|approved|rejected|all`** — **(v15 신규)** 심사 대상 공급자 목록. 승인 API는 있는데 **무엇을 승인할지 찾는 경로가 없었던** 공백 보완. 공개 프로필 + `private/profile`(자격증 이미지·심사 상태·감사로그) + `users.identityVerifiedAt`을 합쳐 내려보냅니다 — 관리자 전용이므로 자격증 이미지가 여기 포함되는 것이 맞습니다(2-2).
  - **`approvalStatus`로 직접 쿼리하지 않습니다.** 그 값은 `private/profile` 하위 문서에 있어 컬렉션그룹 쿼리(`private`)가 필요한데, 같은 이름의 `users/{uid}/private/identity`가 같은 그룹에 섞이고 별도 인덱스도 생깁니다. 공급자 수가 수백 단위인 동안에는 `users`에서 `role=='provider'`를 훑어 하위 문서를 붙이는 편이 단순합니다(12-4 — 하루 수십 건 규모). **잘림은 응답의 `truncated`로 알립니다** — 조용히 자르면 "심사 대기가 없는 것"처럼 보입니다
- **`GET /admin/programs?status=pending_review|published|hidden|draft`** — **(v15 신규)** 심사 대상 프로그램 목록. 공급자 활동명을 함께 붙여 내려보냅니다. `orderBy`를 붙이지 않고 메모리에서 정렬합니다 — `status` 등호 + 다른 필드 정렬은 복합 인덱스를 요구하는데, 심사 대기는 많아야 수십 건이라 인덱스를 하나 더 만들 이유가 없습니다(7번)
- `POST /admin/providers/{id}/approve` — 승인 시 `private/profile.approvalStatus`와 공개 프로필의 `verified`를 함께 갱신, `POST /admin/programs/{id}/review` — **(v10)** `reviewedBy`/`reviewedAt`/`reviewNote` 기록 + **하위 `schedules`의 `programStatus` 일괄 갱신**(collectionGroup 보안규칙이 이 값을 보므로 누락 시 게시해도 검색에 안 잡힘). **(v13 추가)** 승인 시 `publishedAt = publishedAt ?? now()`를 함께 기록하고 파생 필드(`targetAgeTags`·`sido`·`requiresChildInfo`·`difficulty`)를 재산출합니다 — **이걸 빼면 신규순 정렬의 기준 필드를 아무도 채우지 않습니다.** 승인 직후 `rebuildSearchIndex`를 1회 즉시 호출해 검색 반영 지연을 없앱니다
- `GET /admin/settlements`, `POST /admin/settlements/{id}/pay` — **`settlements/{id}/items` 생성 포함**
- **`POST /admin/users/{id}/status`** — **(v10 신규)** 회원 상태 변경(`active`/`suspended`/`withdrawn`). 4번 enum에 값만 있고 전환 경로가 없던 공백 보완. 탈퇴도 문서 삭제가 아니라 이 엔드포인트로 `withdrawn` 처리
- **`GET /admin/providers/{id}/violations`** — (v4 신규) 공급자 취소 이력 조회, **`POST /admin/providers/{id}/restriction/lift`** — (v4 신규) `suspended` 상태 수동 해제

### 외부 연동
- `GET /external/weather`, `GET /external/kakao-map/search`
- 알림 발송: 예약 확정/일정 변경/1:1 문의 답변 도착 시 자동 트리거 → 알림톡 → 실패 시 SMS fallback

## 6. Firestore 보안 규칙 (v10 전면 재작성)

> **v9까지의 규칙은 배포조차 되지 않는 상태였습니다.** 정의되지 않은 함수 3개(`isAdmin`, `isOwner`, `isOwnerOfProgram`)를 호출하고 있어 컴파일 에러가 나고, 컬렉션 7종에는 `match` 블록 자체가 없어 기본 거부에 걸립니다. 아래는 그 두 문제를 해결하고 권한 상승 경로를 막은 전체 규칙입니다.

### 6-0. 설계 원칙 4가지

1. **돈·상태가 걸린 컬렉션은 클라이언트 쓰기 전면 금지.** `bookings`, `payments`, `settlements`, `reviews`는 Cloud Functions(Admin SDK)로만 씁니다.
2. **권한 필드는 생성 시점에도 막는다.** `update`만 막고 `create`를 열어두면 회원가입 요청에 권한 필드를 실어 보내는 방식으로 우회됩니다.
3. **공개 정보와 민감 정보는 문서를 나눈다.** 규칙으로 필드를 가릴 수 없으므로 구조로 해결합니다(2-2 참고).
4. **관리자 판별은 Custom Claims로 한다.** 문서 조회 방식은 규칙 평가마다 읽기 비용이 발생하고, 규칙 내 `get()` 호출 한도(요청당 10회)를 잠식합니다.

### 6-1. 전체 규칙

```javascript
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {

    // ============ 공통 함수 (v10 신규 — v9까지 정의 자체가 없었음) ============
    function isSignedIn() {
      return request.auth != null;
    }

    // Custom Claims 방식. 관리자 지정 스크립트에서
    // admin.auth().setCustomUserClaims(uid, { admin: true })를 함께 실행해야 함
    function isAdmin() {
      return isSignedIn() && request.auth.token.admin == true;
    }

    function isSelf(uid) {
      return isSignedIn() && request.auth.uid == uid;
    }

    // 수정하려는 필드에 금지 목록이 포함됐는지
    function changed(keys) {
      return request.resource.data.diff(resource.data).affectedKeys().hasAny(keys);
    }

    function programOf(programId) {
      return get(/databases/$(database)/documents/programs/$(programId)).data;
    }

    // ============ users ============
    match /users/{uid} {
      allow read: if isSelf(uid) || isAdmin();

      // (v10) 권한 상승 차단 — 생성 시 role/status를 클라이언트가 정할 수 없음.
      // 값을 아예 안 보내거나 기본값으로 보낸 경우만 통과시킴.
      allow create: if isSelf(uid)
        && request.resource.data.get('role', 'consumer') == 'consumer'
        && request.resource.data.get('status', 'active') == 'active';

      allow update: if isSelf(uid) && !changed(['role', 'status']);
      allow delete: if false;      // 탈퇴는 서버에서 status='withdrawn' 처리
      // 관리자에게도 클라이언트 쓰기를 열지 않습니다 — role 부여는
      // Admin SDK 스크립트 전용(12-3). 여기서 열면 브라우저에서 남의 role을
      // 바꿀 수 있게 되어 12-3의 서술과 어긋납니다.
    }

    // (v11 신규) users/{uid}/private/identity — 본인확인 결과
    match /users/{uid}/private/{docId} {
      allow read: if isSelf(uid) || isAdmin();
      allow write: if false;      // POST /auth/identity/verify 에서만 기록
    }

    // ============ providerProfiles — 공개 프로필 ============
    match /providerProfiles/{uid} {
      allow read: if true;         // 프로그램 상세에 운영자 정보 표시
      allow write: if false;       // 심사 결과 반영은 서버 전용
    }

    // 민감 정보 — 상위 문서의 공개 읽기는 여기 상속되지 않음 (2-2 주의사항 참고)
    match /providerProfiles/{uid}/private/{docId} {
      allow read: if isSelf(uid) || isAdmin();
      allow write: if false;
    }

    match /providerProfiles/{uid}/violations/{violationId} {
      allow read: if isSelf(uid) || isAdmin();
      allow write: if false;       // /bookings/{id}/cancel 함수에서만 기록
    }

    // ============ programs ============
    match /programs/{id} {
      allow read: if resource.data.status == 'published'
                || isSelf(resource.data.providerId)
                || isAdmin();

      // 생성은 POST /programs(Cloud Function) 전용.
      // 규칙을 명시하지 않아 기본 거부되며, 이는 의도된 설계임 —
      // 클라이언트 생성을 열면 status='published'로 심사를 우회할 수 있음.

      // (v10) 공급자 직접 수정은 draft 단계에서만.
      // published 상태에서 제목·설명·이미지를 자유롭게 바꿀 수 있으면
      // "관리자가 내용을 확인하고 승인한다"는 전제가 무너집니다(승인 후 내용 교체).
      // 심사 후 수정은 PATCH /programs/{id} 경유 → 핵심 필드가 바뀌면
      // 서버가 status를 pending_review로 되돌려 재심사시킵니다.
      // draft 단계에서는 가격을 포함해 자유롭게 수정 가능(아직 심사 전).
      //
      // (v13 정정) 금지목록 → 허용목록으로 반전.
      // v13이 파생 필드 10여 개를 추가하면서, 금지목록 방식으로는
      // 새 필드가 전부 클라이언트에 열린 상태가 됐습니다.
      // ratingAvg=5.0 / bookingCount30d=999999 를 직접 써서 검색 1위를
      // 차지하거나, sido를 바꿔 다른 지역 검색에 노출되거나,
      // scheduleDates를 심어 회차가 0건인데 달력에 뜨게 만들 수 있었습니다.
      // 필드를 추가할 때 목록에 넣는 걸 잊으면 "저장이 안 되는 버그"로
      // 드러나므로, 잊었을 때 보안 사고가 되는 금지목록보다 안전합니다.
      allow update: if isSelf(resource.data.providerId)
        && resource.data.status == 'draft'
        && request.resource.data.diff(resource.data).affectedKeys()
             .hasOnly(['title', 'description', 'category', 'qualificationType',
                       'location', 'price', 'capacity', 'minCapacity',
                       'scheduleType', 'availableFrom', 'availableUntil',
                       'imageUrls', 'barrierFree',
                       'targetAgeMin', 'targetAgeMax',
                       'walkingDistanceM', 'rainAlternative', 'updatedAt'])
        // (v13 정정) 값 검증은 반드시 get(키, 기본값)으로 씁니다.
        // request.resource.data.price >= 0 처럼 직접 참조하면
        // 그 필드가 없는 문서에서 규칙 평가가 에러로 끝나 거부됩니다 —
        // "가격을 아직 안 넣은 draft는 제목도 못 고치는" 상태가 됩니다.
        && request.resource.data.get('price', 0) >= 0
        && request.resource.data.get('capacity', 0)
             >= request.resource.data.get('minCapacity', 0)
        && request.resource.data.get('rainAlternative', 'none')
             in ['indoor', 'reschedule', 'none']
        // targetAge는 명시적 null(=제한 없음)이 정상값이라 null을 먼저 걸러냅니다.
        && (request.resource.data.get('targetAgeMin', null) == null
            || request.resource.data.get('targetAgeMax', null) == null
            || request.resource.data.targetAgeMin
               <= request.resource.data.targetAgeMax);
      // 파생 필드(targetAgeTags·sido·requiresChildInfo·difficulty·
      // scheduleDates·nextScheduleAt·lastScheduleAt·publishedAt·
      // ratingAvg·ratingCount·bookingCount30d)는 허용목록에 없으므로
      // 클라이언트가 값을 넣으면 수정 전체가 거부됩니다 — 서버 전용입니다.

      allow delete: if false;
      // 관리자도 클라이언트에서 직접 쓰지 않습니다 — 심사는 반드시
      // POST /admin/programs/{id}/review 경유(감사로그 기록 때문).
      // allow write: if isAdmin() 을 넣으면 감사로그를 남기지 않는 우회 경로가 됩니다.
    }

    // 경로 지정 조회용
    match /programs/{programId}/schedules/{scheduleId} {
      allow read: if programOf(programId).status == 'published'
                || isSelf(programOf(programId).providerId)
                || isAdmin();
      allow write: if false;       // 정원(remainingSlots) 조작 방지
    }

    // (v10 필수) collectionGroup 쿼리용 재귀 와일드카드.
    // 7번의 "전체 프로그램에서 특정 날짜 회차 검색"은 collectionGroup 쿼리인데,
    // 위 경로 지정 규칙만으로는 전부 거부됩니다 — 컬렉션 그룹 쿼리는
    // {path=**} 형태의 규칙에서만 허용되기 때문입니다.
    // 이 규칙은 문서에 비정규화 저장한 필드만 보고 판단하므로
    // schedules 문서에 programId / programStatus를 함께 저장해야 합니다(2-4).
    // (v13 명시) 여기에는 isAdmin() 절이 일부러 없습니다.
    // 관리자 화면은 /admin/* 서버 API(Admin SDK)로 조회하므로
    // 클라이언트에서 컬렉션그룹 쿼리를 돌릴 일이 없습니다.
    // 관리자가 draft 회차를 봐야 할 때는 경로 지정 조회를 쓰고,
    // 그쪽 규칙에는 isAdmin()이 있습니다.
    match /{path=**}/schedules/{scheduleId} {
      allow read: if resource.data.programStatus == 'published';
      allow write: if false;
    }
    // ⚠️ 프론트엔드는 이 쿼리에 반드시 필터를 함께 넣어야 합니다.
    //    collectionGroup(db, 'schedules')
    //      .where('programStatus', '==', 'published')   // ← 없으면 permission-denied
    //      .where('startAt', '>=', from).where('startAt', '<=', to)
    //    Firestore는 쿼리 결과를 문서마다 검사하지 않고, "규칙이 보장하는 조건을
    //    쿼리가 스스로 걸었는지"로 통과 여부를 판단하기 때문입니다.
    //    공급자 본인의 미게시(draft) 회차는 이 경로로 조회되지 않으므로,
    //    공급자 대시보드는 경로 지정 조회(programs/{id}/schedules)를 씁니다.

    match /programs/{programId}/scheduleTemplates/{templateId} {
      allow read: if isSelf(programOf(programId).providerId) || isAdmin();
      allow write: if false;       // 캐스케이딩 정책 우회 방지
    }

    // ============ bookings / payments ============
    match /bookings/{id} {
      allow read: if isSelf(resource.data.consumerId)
                || isSelf(resource.data.providerId)
                || isAdmin();
      allow write: if false;
    }

    match /payments/{id} {
      allow read: if isSelf(resource.data.consumerId) || isAdmin();
      allow write: if false;
    }

    // ============ settlements (v10 신규 — v9에 규칙이 없어 공급자가 자기 정산을 못 봤음) ============
    match /settlements/{settlementId} {
      allow read: if isSelf(resource.data.providerId) || isAdmin();
      allow write: if false;
    }

    match /settlements/{settlementId}/items/{itemId} {
      allow read: if isAdmin();    // 건별 명세는 관리자만 (상위 문서로 요약 확인)
      allow write: if false;
    }

    // ============ reviews (v10 — 서버 전용으로 전환) ============
    match /reviews/{reviewId} {
      allow read: if true;

      // v9 규칙은 "예약이 completed인가"만 검사해서, 남의 완료 예약 ID를 알면
      // 아무 프로그램에나 리뷰를 쓸 수 있었음. 검증 항목이 5가지(예약 소유권,
      // programId·providerId 일치, 평점 범위, 문서ID=bookingId)로 늘어나
      // 규칙 내 get() 호출이 누적되므로 POST /reviews 서버 함수로 일원화함.
      allow write: if false;
    }

    // ============ inquiries (v10 신규 — 규칙이 없어 1:1 문의가 동작 불가였음) ============
    match /inquiries/{inquiryId} {
      allow read: if isSelf(resource.data.consumerId)
                || isSelf(resource.data.providerId)
                || isAdmin();
      allow write: if false;       // POST /inquiries 경유 (알림톡 트리거 포함)
    }

    match /inquiries/{inquiryId}/messages/{messageId} {
      allow read: if isSelf(get(/databases/$(database)/documents/inquiries/$(inquiryId)).data.consumerId)
                || isSelf(get(/databases/$(database)/documents/inquiries/$(inquiryId)).data.providerId)
                || isAdmin();
      allow write: if false;       // POST /inquiries/{id}/messages 경유
    }

    // ============ voucherAds ============
    match /voucherAds/{adId} {
      allow read: if resource.data.status == 'active' || isAdmin();
      allow write: if isAdmin();
    }

    // ============ termsAgreements (v10 신규) ============
    match /termsAgreements/{agreementId} {

    }

    match /notificationLogs/{logId} {
      allow read: if isAdmin();
      allow write: if false;
    }

    // ============ aggregates (v13 신규 — 검색 캘린더·홈 지표 집계) ============
    match /aggregates/{docId} {
      allow read: if true;         // 파생 집계값만 담김. 개인정보 금지(2-13)
      allow write: if false;       // syncProgramScheduleDates 등 서버 배치 전용
    }

    // ============ 명시하지 않은 모든 경로는 기본 거부 ============

  }
```

### 6-2. 보안규칙으로 막히지 않는 것 (반드시 서버에서 처리)

**Firestore 보안규칙은 클라이언트 SDK 접근에만 적용됩니다.** Cloud Functions는 서비스 계정 권한으로 도는 Admin SDK를 쓰므로 규칙을 완전히 우회합니다. 따라서 다음 두 가지는 규칙이 아니라 함수 코드에서 처리해야 합니다.

**① `/admin/*` 엔드포인트의 권한 검사** — 이게 빠지면 API 주소를 아는 일반 사용자가 정산 지급을 그대로 실행할 수 있습니다. 프론트엔드 라우트 가드는 보안 장치가 아닙니다.

**(v13 정정) 예시 코드를 실제 채택 구조로 교체했습니다.** 원래 예시는 callable 함수(`onCall`) 문법이었는데, 5번의 API 목록은 전부 `POST /admin/...` 형태의 REST 경로입니다. 둘은 구현 방식이 달라 하나를 골라야 했고, **REST(`onRequest` + Express 라우터)로 확정**했습니다 — 결제 웹훅(`POST /payments/webhook`)은 외부 PG가 호출하므로 callable로는 아예 받을 수 없고, 라우터 하나에 경로를 모으면 콜드 스타트와 비용도 유리하기 때문입니다. 아울러 예시가 `firebase-functions` v1 문법이라 v2 기준으로 다시 썼습니다.

```typescript
// /admin/* 라우터에 미들웨어로 한 번만 붙입니다.
// 경로마다 각자 검사하게 두면 새 엔드포인트에서 빠뜨립니다.
async function requireAdmin(req, res, next) {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return next(new AppError('unauthenticated'));

  // checkRevoked는 P1 — 지금은 false, /admin/*과 정산에만 켤 예정(아래 ②)
  const decoded = await admin.auth().verifyIdToken(token, false);
  if (decoded.admin !== true) {
    return next(new AppError('permission-denied', '관리자 권한이 필요합니다'));
  }
  req.auth = decoded;
  next();
}

adminRouter.use(requireAdmin);
```

> **(v14 정정) HTTP 상태 코드를 손으로 넘기지 않습니다.** 처음 예시는 `new AppError('unauthenticated', 401)`처럼 코드와 상태를 함께 적었는데, 그러면 `permission-denied`에 401을 붙이는 식의 불일치가 생기고 컴파일러가 잡아주지 못합니다. **코드 하나에서 상태를 유도**하는 방식으로 바꿨습니다 — `unauthenticated`=401 / `permission-denied`=403 / `invalid-argument`·`failed-precondition`=400 / `not-found`=404 / `internal`=500.

> **이 미들웨어가 유일한 차단선입니다.** 보안규칙은 Admin SDK에 적용되지 않으므로, 여기를 통과하면 Firestore의 어떤 문서든 읽고 쓸 수 있습니다. 반드시 테스트로 고정하세요(6-3의 관리자 케이스).

> **CORS 처리를 잊지 마세요.** callable 함수는 CORS를 자동으로 처리해주지만 `onRequest`는 직접 해야 합니다. 브라우저에서 호출하면 요청이 막힙니다. **권장 방식은 Firebase Hosting의 rewrite로 `/api/**`를 함수에 연결하는 것**입니다 — 같은 도메인이 되어 CORS 자체가 발생하지 않고, 프론트엔드는 상대경로만 쓰면 됩니다.

**② 즉시 차단이 필요한 경우의 토큰 무효화** — Custom Claims는 이미 발급된 ID 토큰에 소급 적용되지 않습니다. 권한을 회수해도 기존 토큰이 만료(기본 1시간)될 때까지 유효합니다.

- **권한 부여 시:** 대상자가 재로그인하거나 `getIdToken(true)`로 토큰을 강제 갱신해야 반영됩니다
- **권한 회수 시:** `admin.auth().revokeRefreshTokens(uid)`를 함께 호출하고, `/admin/*` 함수에서는 `verifyIdToken(token, true)`로 무효화 여부까지 확인합니다
- **적용 범위:** `checkRevoked=true`는 호출마다 Auth 서버 왕복이 붙어 수십 ms가 추가되므로 **`/admin/*`과 정산 관련 엔드포인트에만** 켜고 일반 API에는 끕니다

## 7. 인덱스 필요 사항

- `schedules`(컬렉션 그룹): **`programStatus` + `startAt`** — 전체 프로그램에서 날짜별 회차를 검색하는 용도. 보안규칙이 `programStatus`를 요구하므로 쿼리 필터도 이 필드를 쓰고 인덱스도 여기에 맞춰야 함 **(v10 정정 — 기존의 `programId + startAt`은 "특정 프로그램의 회차 목록"용이라 전체 검색과 맞지 않음)**
- `schedules`(단일 컬렉션): `programId` + `startAt` — 특정 프로그램의 회차 목록 조회용
- `bookings`: `providerId` + `status`, `consumerId` + `status`, **`status` + `expiresAt`(만료 홀드 배치 조회용, 신규)**
- `programs`: `status` + `location`(geohash 방식) — 거리순 정렬용. 기존의 `qualificationType` 조합은 `category`와 사실상 같은 축이라 제외 **(v13 정정)**
- `programs`: **검색·필터용 복합 인덱스는 만들지 않습니다** **(v13 확정)**

> **(v13) 검색 필터에는 인덱스를 만들지 않습니다.** 필터 7종 × 정렬 6종을 전부 복합 인덱스로 만들면 관리 불가능한 행렬이 되고, 필터를 하나 추가할 때마다 인덱스가 배로 늘어납니다. `GET /programs/search`는 **집계 문서 `aggregates/searchIndex` 1건만 읽어** 필터·정렬을 메모리에서 처리하므로 인덱스가 필요 없습니다(17-1). 집계를 만드는 `rebuildSearchIndex` 배치는 `where(status=='published')` 단일 필드 쿼리라 자동 색인으로 충분합니다.
>
> **`nextScheduleAt`을 인덱스에 넣지 마세요.** 초안에는 `status + sido + nextScheduleAt` 조합이 있었는데, Firestore는 **인덱스에 쓰인 필드에 값이 없는 문서를 아예 색인하지 않아** 회차가 없는 상시모집(`open`) 프로그램이 검색에서 통째로 사라집니다(17-2).

### 7-1. 구현 시 참고 팁 (스키마 변경 아님, 코딩 시 체크리스트)

- **`releaseExpiredHolds` 주기:** 처음부터 1분 단위로 돌릴 필요 없음. 초기 트래픽이 적으므로 5분 주기로 시작하고, 실제 예약 경쟁이 빈번해지면 그때 좁히면 충분.
- **타임존:** Firestore `timestamp`는 이미 UTC 기반 절대시각이라 스키마 자체는 문제 없음. 단, `scheduleTemplates.timeOfDay`("10:00" 같은 문자열, KST 기준)를 `schedules.startAt`(timestamp)으로 변환하는 Cloud Function 로직에서 KST→UTC 환산을 명시적으로 처리해야 함 — 이 변환 지점 하나만 조심하면 됨.
- **지오쿼리:** geohash는 카카오맵 기능이 아니라 Firestore 반경검색용 저장 전략(`geofire-common` 라이브러리). "Firestore에서 geohash로 후보 검색 → 결과를 카카오맵 SDK로 화면에 표시"로 역할이 분리된다는 점을 구분해서 구현.

## 9. 개발 협업 전략 (Git / GitHub, v6 신규)

8/13부터 프론트엔드·백엔드로 작업이 갈라지므로, 코드를 어디에 두고 어떻게 나눠서 작업할지를 스키마 문서에 함께 못박아 둡니다. (이 섹션은 DB/API 설계가 아니라 개발 운영 방식이라 위 스키마 내용과는 독립적입니다.)

### 9-1. 저장소: GitHub

코드는 GitHub 저장소 하나에 둡니다. 구글드라이브는 문서(벤치마킹 리포트, 사업자등록증, 발표자료 등) 공유용으로는 계속 쓰되, 소스코드는 올리지 않습니다 — 실시간 동시편집은 되지만 같은 코드 파일을 두 사람이 동시에 고치면 사본(`파일명 (1).js`)이 생기거나 덮어써지고, 커밋 이력·브랜치·코드리뷰 같은 기능이 없어 협업에 부적합합니다.

### 9-2. 브랜치 전략: GitHub Flow

GitFlow(다중 버전이 동시에 운영되는 소프트웨어에 적합 — 예: 앱스토어에서 v1.2/v1.3이 동시에 서비스되는 경우)가 아니라, **GitHub Flow**를 채택합니다. 이유는 품(FOOM)이 항상 최신 버전 하나만 운영되는 웹서비스이고, 지금 팀 규모(프론트 1명, 백엔드 1명 수준)에는 GitFlow의 `develop`/`release` 같은 다단계 브랜치 구조가 오버엔지니어링이기 때문입니다.

절차:
1. `main` 브랜치에서 기능별 브랜치 생성 — 네이밍 규칙: `feature/영역-기능명` (예: `feature/frontend-login`, `feature/backend-booking-api`)
2. 각자 브랜치에서 개발·커밋
3. 완료되면 Pull Request(PR) 생성
4. 상대방(또는 팀장)이 코드리뷰 후 `main`에 병합
5. 병합 즉시 배포

**전제 조건:** `main`은 항상 배포 가능한 상태를 유지해야 합니다. 이를 위해 PR을 올릴 때마다 자동 테스트(CI)가 돌아가야 하고, `main`이 깨지는 상황은 팀 전체가 즉시 멈춰서 고치는 규칙으로 삼습니다. 아직 CI가 없다면 최소한 병합 전 "로컬에서 빌드/실행 확인" 정도는 팀 규칙으로 정해두는 것을 권장합니다.

### 9-3. 클로드(Claude Code/Cowork)의 역할

클로드는 코드를 별도로 저장하거나 호스팅하지 않습니다. GitHub 커넥터로 이 저장소에 직접 연결해서, 코드를 읽고, 필요하면 브랜치를 만들거나 PR을 올리는 "협업자"로 동작합니다. 즉 "클로드 안에서 공유 vs GitHub에서 공유"가 아니라, **코드의 원본은 항상 GitHub에 두고 클로드는 그 저장소에 붙어서 작업하는 조합**이 맞는 사용 방식입니다. 팀원 각자의 노트북에서 GitHub 커넥터 연결 상태만 확인하면 됩니다(연결이 끊기면 클로드가 해당 팀원의 최신 코드를 못 봅니다).

### 9-4. 실행 항목

### 9-5. UI 컴포넌트/디자인 시스템 (v7 신규, v8 컬러 확정 추가)

로드맵에 "토스 미니앱 스타일 참고"라고 적어둔 부분에 대한 결론입니다. **토스 디자인 시스템(TDS)은 그대로 가져다 쓸 수 없습니다** — TDS는 "앱인토스"(토스 앱 안에서 도는 미니앱)를 만드는 파트너사에게만 제한적으로 열린 폐쇄형 시스템이고, 토스 개발자센터 문서에 "파트너사는 앱인토스 서비스를 이용하는 범위 안에서만 이 자료를 쓸 수 있다"고 명시되어 있어 품(FOOM) 같은 독립 웹서비스에는 라이선스상 사용할 수 없습니다.

대신 **Tailwind CSS + shadcn/ui** 조합을 채택했습니다. 완전 무료(MIT 라이선스)이고, 토스류의 깔끔한 핀테크 톤을 라이선스 걱정 없이 낼 수 있는 업계 표준 조합입니다.

**대표 컬러 (v8 확정):**
- 메인 컬러: `#1F5C43` (포레스트 그린) — "자연치유" 정체성과 맞는 색으로, 지금까지 만든 결재요청서·프론트엔드·스키마 문서에 이미 일관되게 써온 색을 정식 확정. shadcn/ui 표준 CSS 변수(`--primary` 등)에 매핑되어 있음
- 보조/배경 톤: 옅은 민트그린(`#EAF3ED` 계열)을 카드·배경 강조에 사용

**폰트 (v9 확정):** 본문·제목 모두 **Pretendard** 단독으로 갑니다. 디자인 초안에 들어있던 `Toss Product Sans`/`Tossface`는 사용하지 않습니다 — 위에서 TDS를 배제한 것과 같은 이유(토스 자산은 앱인토스 파트너 범위로 한정)이고, 초안이 참조하던 CDN 경로도 공식 배포 채널이 아닙니다. Pretendard는 SIL Open Font License 1.1이라 상업적 사용·재배포에 제약이 없고, 한글 자소 균형이 토스체와 가장 가까워 초안의 인상을 거의 그대로 유지할 수 있습니다. 이모지는 별도 웹폰트 없이 사용자 OS 기본 이모지를 씁니다.

**배경색 규칙 (v8 신규):** 라이트 모드 기본 배경은 순백(`#FFFFFF`)으로 통일. 다크 모드는 별도 토글 없이 **사용자 시스템(OS) 설정을 그대로 따라가도록** 구현(`prefers-color-scheme` 미디어쿼리 기반) — 사용자가 직접 라이트/다크를 고르는 스위치는 1차 오픈 범위에 넣지 않음.

### 9-6. 작업 도구 구분: Claude Code CLI ↔ Cowork (v8 신규, v10 정정)

> **v10 정정:** v8에는 "Cowork는 파일을 zip으로 주고받는 구조라 코딩에 비효율적"이라고 적혀 있었으나 **사실과 다릅니다.** Cowork도 로컬 폴더를 연결하면 소스 파일을 직접 읽고 수정합니다(2026-08-11에 실제로 `foom-frontend` 코드를 직접 수정했습니다). 따라서 "Cowork로는 코딩을 못 한다"가 아니라 **"수정 → 실행 → 확인 왕복이 잦은 작업은 CLI가 빠르다"**가 정확한 구분입니다.

**실제 차이는 하나입니다 — 실행 결과를 그 자리에서 보느냐.** Claude Code CLI는 내 컴퓨터에서 돌기 때문에 `npm run dev`를 띄우고 에러를 즉시 읽어 고칠 수 있습니다. Cowork는 격리된 환경에서 빌드·테스트만 검증할 수 있고, 실제 화면 확인은 사람이 해서 알려줘야 합니다. 파일 수가 늘고 디버깅 왕복이 잦아질수록 이 차이가 벌어집니다.

| | Claude Code CLI (로컬) | Cowork (데스크톱 앱) |
|---|---|---|
| **주 용도** | 기능 구현, 리팩터링, 버그 수정, 테스트 | 기획·리서치·문서, 의사결정 기록 |
| 로컬 파일 수정 | O | O (폴더 연결 시) |
| 개발 서버 실행·디버깅 | **O** | X (빌드·타입체크만 가능) |
| git 커밋·브랜치·PR | **O** (같은 터미널에서) | O (GitHub 커넥터 경유) |
| 노션·메일·캘린더 연동 | X | **O** |
| 웹 검색·문서 생성(docx/pptx) | 제한적 | **O** |

**권장 사용 방식:** 8/13 개발 착수 이후 **코딩은 CLI를 주력**으로, **문서·커넥터 작업만 Cowork**로 가져옵니다. 설치는 `npm install -g @anthropic-ai/claude-code`, 프로젝트 폴더에서 `claude` 실행 후 로그인. 팀원 각자 로컬에 설치해 자기 브랜치(`feature/영역-기능명`, 9-2 참고)에서 작업합니다.

## 12. 관리자 페이지 (v9 신규)

### 12-1. 왜 필요한가

관리자 화면은 "있으면 좋은 것"이 아니라 **없으면 서비스가 돌아가지 않는 필수 구성요소**입니다. 지금까지의 결정들이 사람의 판단을 전제로 설계돼 있기 때문입니다.

1. **공급자 자격증 수기 검토** — 자격증 진위 자동 검증 API를 쓰지 않고 관리자 수기 검토로 결정했습니다(벤더 선정 문서 참고사항). 제출된 `private/profile.certificateImageUrls`(v10에서 민감정보 하위 문서로 분리 — 2-2 참고)를 사람이 열어보고 `approvalStatus`를 `approved`/`rejected`로 바꿔줄 화면이 필요합니다. 승인 시 공개 프로필의 `verified`도 함께 `true`로 갱신합니다.
2. **프로그램 게시 승인** — 보안규칙(6번)상 공급자는 `programs.status`를 직접 `published`로 바꿀 수 없습니다. 공급자가 `POST /programs/{id}/submit-for-review`로 심사를 요청하면, 관리자가 내용·가격을 확인하고 승인해야 비로소 노출됩니다. 조사한 벤치마킹 대상 5개 플랫폼 전부 자동 게시 없이 운영자 검수를 거칩니다(리포트 4.6).
3. **정산 지급 처리** — 수수료 10%와 원천징수 3.3%가 반영된 `settlements`/`settlements/{id}/items`를 확인하고 `status='paid'`로 넘기는 것은 돈이 나가는 행위라 자동화 대상이 아닙니다.
4. **공급자 제재 관리** — 무단 취소 누적으로 `suspended`가 된 공급자의 `violations` 이력을 조회하고, 소명이 인정되면 `POST /admin/providers/{id}/restriction/lift`로 해제해야 합니다.

### 12-2. MVP 구현 범위 — 탭 3개

1차 오픈 단계에서는 지표 대시보드 없이 **목록 + 상세 + 승인 버튼**으로 이루어진 단순 테이블 화면 3개면 충분합니다.

| 탭 | 하는 일 | 연동 API | 상태 |
|---|---|---|---|
| 전문가 심사 | `approvalStatus='pending'` 목록 → 자격증 이미지 확인 → 승인/반려 | `GET /admin/providers`, `POST /admin/providers/{id}/approve` | **구현됨 (v15)** |
| 프로그램 심사 | `status='pending_review'` 목록 → 내용·가격 확인 → 게시/반려 | `GET /admin/programs`, `POST /admin/programs/{id}/review` | **구현됨 (v15)** |
| 정산 관리 | 기간·공급자별 정산 조회 → 지급 완료 처리 | `GET /admin/settlements`, `POST /admin/settlements/{id}/pay` | 미구현 — 예약·결제가 없어 정산할 거래가 생기지 않음 |

> **(v15) 반려는 사유가 필수입니다.** 두 심사 API 모두 `{ decision: 'approved'|'rejected', note }`를 받고, `rejected`인데 `note`가 비어 있으면 거부합니다. 사유는 공급자에게 그대로 노출되는 값이라(2-3 `reviewNote`), 비어 있으면 **무엇을 고쳐야 할지 알 수 없어 재제출이 불가능해집니다.**
>
> **(v15) 게시 승인은 `pending_review`에서만 됩니다.** 이미 게시된 프로그램의 내용 수정은 `PATCH /programs/{id}`가 재심사로 되돌리는 경로를 씁니다(2-3 v10). 심사 버튼에 게시 취소를 겸하게 하면 "심사"와 "운영 중 조치"가 한 버튼에 섞입니다. 게시 취소가 필요해지면 별도 엔드포인트를 둡니다.

공급자 제재 관리(`GET /admin/providers/{id}/violations`, `POST /admin/providers/{id}/restriction/lift`)는 **2차**로 미룹니다 — 페널티는 예약이 쌓이고 취소가 발생한 뒤에야 실제로 필요해지는 기능이라 오픈 시점에 없어도 운영에 지장이 없습니다.

### 12-3. 관리자 다인 운영 방식

**공용 아이디를 쓰지 않습니다.** 관리자가 여러 명이어도 각자 개인 계정으로 가입한 뒤, 그 계정에만 권한을 부여합니다.

1. 관리자 각자가 일반 사용자와 동일하게 회원가입(카카오·네이버 소셜 2종 — **(v13 정정)** 문자인증 가입은 15-1에서 폐기됐는데 이 문장에 잔재가 남아 있었습니다)
2. 해당 계정의 `users.role`을 `admin`으로 지정 **하고, 동시에 `setCustomUserClaims(uid, { admin: true })`도 실행** — 보안규칙의 `isAdmin()`은 Custom Claims만 보므로 둘 중 하나만 하면 화면이 열리지 않습니다
3. `/admin` 주소로 접속 → 권한 검사 통과 시 화면 진입

공용 계정 대신 개인 계정을 쓰는 이유는 세 가지입니다. **책임 추적** — "누가 언제 어느 공급자를 승인했는지"가 남습니다(`private/profile.approvedBy`/`approvedAt`, `programs.reviewedBy`/`reviewedAt`). **인수인계** — 담당자가 바뀌면 그 사람의 `role`만 내리면 되고, 나머지 인원의 비밀번호를 바꿀 필요가 없습니다. **유출 범위 축소** — 계정 하나가 뚫려도 그 계정만 잠그면 됩니다.

**관리자 화면 진입 경로 (v9 확정):** 헤더 프로필 영역에 **조건부 메뉴**를 둡니다. 로그인한 사용자의 `role`이 `admin`일 때만 드롭다운에 "관리자" 항목이 렌더링되고, 게스트와 일반 회원에게는 DOM 자체가 만들어지지 않습니다. 링크를 아예 걸지 않고 관리자가 `/admin`을 북마크해서 들어오는 방식도 검토했으나, **보안 수준은 두 방식이 동일하고**(실제 차단은 아래 3중 통제에서 이루어짐) 관리자가 여러 명일 때 진입 경로를 따로 공지·관리할 필요가 없어 조건부 메뉴를 택했습니다.

> **메뉴를 숨기는 것은 보안 장치가 아닙니다.** 버튼이 보이지 않아도 누구나 주소창에 `/admin`을 직접 입력할 수 있습니다. 조건부 렌더링은 일반 사용자에게 불필요한 메뉴를 노출하지 않기 위한 UX 처리이고, 실제 차단은 ① 프론트엔드 라우트 가드 ② Cloud Functions 진입부 권한 검사 ③ Firestore 보안규칙 `isAdmin()` 세 곳에서 이루어집니다. ①을 우회해도 ②·③에서 막혀 화면 껍데기만 열릴 뿐 데이터는 내려오지 않습니다 — 상세는 6-2 참고.

**코드 분리:** 관리자 화면은 `React.lazy()`로 지연 로딩해 일반 사용자 번들에서 분리합니다. 보안 목적이 아니라(화면 코드가 노출돼도 데이터가 새지는 않습니다) 소비자 화면의 초기 로딩을 가볍게 유지하기 위한 조치입니다.

> **`role` 부여 방법:** `users.role`은 보안규칙상 클라이언트가 절대 수정할 수 없습니다(2-1, 6번). 또한 보안규칙에서 관리자에게도 클라이언트 쓰기를 열어두지 않았으므로(6-1 — `voucherAds`만 예외. 광고는 감사로그가 필요 없어 콘솔 직접 관리를 허용), 최초 관리자 지정은 **Admin SDK 스크립트 실행**으로만 가능합니다(`users.role`과 Custom Claims를 한 번에 처리해야 하므로 콘솔 수동 편집만으로는 부족합니다). 이 절차 자체를 관리자 화면에 만들어두면 권한 상승 취약점이 되므로 만들지 않습니다.

### 12-4. 비용

**추가 비용 0원입니다.** 관리자 페이지는 별도 서버나 유료 백오피스 솔루션이 아니라 **같은 프로젝트 안의 `/admin` 경로 하나**입니다. Hosting·Functions·Firestore를 소비자 화면과 그대로 공유하고, 접속 빈도가 하루 수십 건 수준이라 Firebase 무료 쿼터 안에서 전부 처리됩니다.

### 12-5. v9에서 발견한 3가지 → v10에서 처리 완료

v9 작성 시점에 지적했던 세 가지는 모두 v10에 반영됐습니다. 이력 확인용으로 남겨둡니다.

| v9 지적 | v10 처리 |
|---|---|
| 보안규칙의 `isAdmin()` 미정의 | 6-1에 Custom Claims 방식으로 정의. `isOwner`/`isOwnerOfProgram`도 정의 자체가 없었던 것을 확인해 `isSelf`/`programOf`로 정리 |
| 프로그램 심사 감사로그 부재 | `programs`에 `reviewedBy`/`reviewedAt`/`reviewNote` 추가 (2-3) |
| Functions 레벨 권한 검사 누락 | 6-2 ①에 공통 적용 코드로 명시 |

## 13. 착수 전 보안 조치 우선순위 (v10 신규)

v10에서 정리한 항목을 처리 시점 기준으로 나눴습니다. **P0는 서비스를 열기 전에 반드시 끝나야 하는 것**이고, 하나라도 빠지면 실제로 뚫리거나 화면이 동작하지 않습니다.

### P0 — 개발 착수 시 즉시 (백엔드 트랙 첫 작업)

| 항목 | 안 하면 생기는 일 | 참고 |
|---|---|---|
| `users` create 필드 검증 | 회원가입 요청 조작으로 **누구나 관리자가 됨** | 6-1 |
| 결제 웹훅 금액 대조 | 프론트 조작으로 **3만 5천 원을 100원에 결제** | 2-6 |
| `/admin/*` 함수 권한 검사 | 로그인 사용자가 **정산 지급 API 직접 호출** | 6-2 ① |
| `providerProfiles` 구조 분리 + 규칙 | 계좌번호를 공개하지 않으면 **운영자 정보가 화면에 안 뜸** | 2-2, 6-1 |
| 누락 컬렉션 7종 규칙 추가 | 정산·문의·약관동의 **조회 자체가 안 됨** | 6-1 |
| 함수 3종 정의 | **규칙 배포가 실패함** | 6-1 |
| 관리자 지정 스크립트 (`setCustomUserClaims` + `users.role` 동시 갱신) | `isAdmin()`이 Custom Claims만 보므로, 이게 없으면 **관리자 화면이 아예 열리지 않음** | 6-1, 12-3 |
| `schedules`에 `programId`/`programStatus` 비정규화 + collectionGroup 규칙 | 날짜별 회차 검색이 **전부 거부되어 검색 화면이 동작 안 함** | 2-4, 6-1 |
| 리뷰 생성 서버 전용 전환 | 남의 예약 ID로 **거짓 리뷰 무한 작성** | 6-1 |

> **데이터가 0건인 지금이 가장 쌉니다.** `providerProfiles` 분리는 데이터 구조 변경이라 실데이터가 쌓인 뒤에는 마이그레이션 작업이 됩니다. Firestore를 8/10에 만들어 아직 비어 있으므로, 착수 시점에 처리하면 비용이 사실상 0입니다.

### P1 — 정식 오픈 전까지

- **`programs`에 대상연령 필드(`targetAgeMin`/`targetAgeMax`) 추가 + 예약 폼 참가자 정보 구현** — **(v12에서 P2 → P1로 올림)** 소비자 본인확인을 제외한 대신 아동 안전을 이 폼으로 확보하기로 했으므로, 유아숲체험을 오픈하려면 선행되어야 합니다(15-6)

- **검색 필터 필드 일괄 추가** — **(v13 신규)** `targetAgeTags`·`difficulty`·`walkingDistanceM`·`rainAlternative`·`region`·`scheduleDates`·`nextScheduleAt`/`lastScheduleAt`·`publishedAt`·`ratingAvg`/`ratingCount`·`bookingCount30d`. 필터 화면은 이미 확정됐으므로(17번) 필드가 없으면 화면을 만들 수 없습니다
- **`GET /programs/search` + `rebuildSearchIndex`·`syncProgramScheduleDates`·`recalcProgramStats`** — **(v13 신규)** 필터를 클라이언트 Firestore 쿼리로 만들면 논리합 30개 제한에 걸립니다(17-1). `recalcProgramStats`가 없으면 인기순·평점순의 기준 필드를 아무도 채우지 않습니다
- **`aggregates/searchIndex`·`scheduleCalendar` 집계 문서 + 보안규칙** — **(v13 신규)** 검색 데이터 소스와 캘린더의 "회차 있는 날" 점 (17-1, 17-5)
- **`programs` 수정 규칙을 허용목록으로 반전 + 6-3 테스트 6종 추가** — **(v13, P0에 가까움)** 금지목록 상태로 두면 공급자가 `ratingAvg`·`bookingCount30d`를 직접 써서 검색 순위를 조작할 수 있습니다(6-1)
- **프로그램 승인 시 `publishedAt` 기록** — **(v13)** 안 하면 신규순 정렬이 동작하지 않습니다(5번)
- **임시 공급자 지정 경로(`grant-provider`) 제거 + 그 계정 재심사** — **(v14 신규)** 본인확인 계약 전까지의 우회로입니다. 남겨두면 심사를 거치지 않은 계정이 그대로 영업하게 됩니다. 상세와 체크리스트는 15-8
- 보안규칙 테스트 15종 구축 및 기능 추가 시 확장 (6-3)
- `/admin/*`·정산 엔드포인트에 `checkRevoked=true` 적용 (6-2 ②)
- 후기 섹션 실제 `reviews` 연동 또는 숨김 처리 (9-7 ④)
- 외부 이미지(Unsplash) → 자체 이미지 + Firebase Storage 교체 (9-7 ⑧)
- **Firebase Storage 설정 + `storage.rules` 배포 + 규칙 테스트 4종** — **(v16 신규)** 설계는 18번. 이게 없으면 **자격증도 프로그램 사진도 없이 심사**하게 됩니다(12-1 ①이 요구하는 "사람이 열어보고 판단"이 성립하지 않음). 규칙을 배포하지 않은 채 버킷만 만들면 콘솔 기본 규칙이 남아 **자격증이 공개될 수 있습니다** — 버킷 생성과 규칙 배포는 반드시 함께 합니다

### P2 — 팀·법률 판단 후

- 아동·청소년 대상 프로그램의 법정 요건 확인 방식 (벤치마킹 리포트 6.3 2단계)
- 공급자 가점 항목(전문업체 소속·운영 이력·보험 가입) 필드화 (동 3단계)
- 산림복지법상 개인 프리랜서 단독 영업 가능 여부 — 이 결론에 따라 공급자 정의 자체가 달라짐 (리포트 7번, 우선순위 높음)
- 화면 대조에서 도출된 스키마 갭 잔여분 — **부대비용**(재료비·입장료·주차비 사전 명시. 벤치마킹 리포트 6.2가 필수로 지목), **홈 집계지표**(등록 전문가 수·누적 프로그램·평균 평점·재참여율. 리포트 3.3이 B2G 영업 근거로 강조 — 자리는 `aggregates/homeStats`로 잡아뒀음), **공급자 활동지역·반경**(고정 장소형/출장형 이원 구조. 리포트 2.4)

> **(v13) 위 목록에서 빠진 것:** **난이도·보행거리**와 **프로그램 평점 캐시**는 v13에서 필터·정렬에 실제로 필요해져 P1으로 올라갔습니다(`difficulty`/`walkingDistanceM`/`ratingAvg`/`ratingCount`). "숲 특화 필터"로 뭉뚱그려 보류해뒀던 항목이 화면을 그려보니 없으면 정렬 자체가 불가능한 필수 필드였습니다.

| **결제(PG)** | 토스페이먼츠 + 포트원(연동 레이어) | 영세·중소 수수료 구간이 4개 주요 PG(토스페이먼츠·KG이니시스·NHN KCP·나이스페이먼츠) 중 **최저**(영세 1.65% ~ 중소3 2.65%). 포트원 경유 시 가입비 면제 + **향후 PG 교체 시 재개발 불필요** | 일반 등급 카드 수수료 3.2%, 초기 가입비 0원(포트원 경유로 약 22만 원 면제) | — |
| **날씨** | 기상청 공공데이터포털 (단기예보·기상특보) | 완전 무료, 카드 등록 불필요, 신청 즉시 자동 승인 | 무료 (개발자 계정 일 10,000건) | OpenWeatherMap — 쿼터는 넉넉하나 한국 기상특보 연동 없음, 국지 정밀도 낮음 |

### 14-1. 함께 결정한 것

- **자격증 검증은 자동화하지 않습니다.** 관리자 수기 검토로 갑니다 — 초기 공급자 수가 적을 때는 사람이 보는 게 충분하다고 판단. 관리자 페이지가 필수가 된 이유이기도 합니다(12번).
- **날씨는 참고용 정보일 뿐 환불정책과 무관합니다.** 초기 문서에 "환불정책이 기상특보 기준"이라고 잘못 적혀 있었으나 정정됐습니다. 우천 시 진행 여부는 **공급자 재량**이고 자동취소 로직은 만들지 않습니다.
- **플랫폼 수수료는 거래액의 10% + 원천징수 3.3%.** 프립 9.9%·마이리얼트립 10%로 액티비티 시장가가 수렴해 있어 그 선에 맞췄습니다(벤치마킹 리포트 4.1). 숨고식 선불 과금(견적 발송 시 건당 과금)은 **채택하지 않습니다** — 유휴 공급자층에 치명적이라는 판단.
- **바우처는 직접 결제 연동 대신 광고료 모델입니다.** PG사가 바우처 인가를 받은 산림복지전문업이 아니라 처리 불가. 바우처 운영 복지업체가 플랫폼에 광고 형태로 게시하고, 결제는 **현장결제로만** 받습니다. (진흥원 회신이 오면 대조 확인 필요 — 미확정 초안)
- **도메인 등록업체는 카페24에 종속되지 않습니다.** Firebase Hosting은 DNS 편집 권한만 요구하므로 어느 등록업체든 무관합니다. 단 `.kr`은 국내 KISA 인증 대행업체를 거쳐야 하고 Cloudflare Registrar는 `.kr`을 지원하지 않습니다.

### 14-2. 이후 변경된 사항 (2026-08-11 확인)

- **카카오맵 API 심사가 폐지됐습니다.** 2026년 7월 21일부터 앱 관리 페이지에서 활성화만 하면 바로 사용 가능(기존에는 추가 기능 신청 + 관리자 심사 필요).
- **대신 무료 쿼터 제공 방식이 바뀌었습니다.** 개발자 계정 기준 **첫 번째로 활성화한 앱에만** 무료 쿼터가 제공됩니다. 개발용·운영용 앱을 따로 만들면 두 번째 앱은 비즈월렛 연결 후 유료입니다 — **앱은 하나로 쓰고 도메인만 여러 개 등록하는 방식을 권장합니다.**
- 지도 Web SDK 무료 쿼터는 일 30만 건(초과 0.1원/건), 주소→좌표 변환 일 10만 건(초과 0.5원/건), 키워드 장소검색 일 10만 건(초과 2원/건).

## 15. 로그인·본인확인 정책 (v11 신규)

### 15-1. 가입은 소셜 2종, 본인확인은 공급자 등록에만 (v12 확정)

| 단계 | 요구 사항 |
|---|---|
| 둘러보기·검색 | 없음 (비로그인 허용) |
| 회원가입 | 카카오 또는 네이버 소셜 |
| 예약·결제 | **본인확인 없음.** 결제 수단 인증은 PG(토스페이먼츠)가 처리 + 예약 폼에서 참가자 정보 입력(15-6) |
| 공급자 등록 | **휴대폰 본인확인 필수** + 자격증 제출 → 관리자 심사 |

**이메일·비밀번호 가입은 만들지 않습니다.** 국내 신규 서비스에서 사라지는 추세이고, 비밀번호를 보관하지 않으면 유출 리스크도 그만큼 줄어듭니다.

#### 왜 소비자 본인확인을 넣지 않는가 (v12 — v11 결정 철회)

v11까지는 결제 시점에 본인확인을 요구하기로 했습니다. 근거는 ① 미성년자 판별 ② 사고 시 신원 확인 ③ 어뷰징 방어였는데, 세 가지 모두 유효하지 않다고 판단했습니다.

**① 미성년자 판별 — 성립하지 않습니다.** 유아숲체험은 **부모가 결제하고 아이가 참가**합니다. 결제자 본인확인으로 얻는 것은 "부모가 성인"이라는 사실뿐이고, 정작 필요한 **참가 아동의 나이는 알 수 없습니다.** 그 값은 예약 폼에서 받아야만 나옵니다.

**② 사고 시 신원 확인 — 예약 폼이 더 정확합니다.** 사고 대응에 필요한 것은 결제자 실명이 아니라 **현장에 있는 참가자의 이름·연령·특이사항(알레르기·지병)과 비상 연락처**입니다. 본인확인 API로는 하나도 얻을 수 없습니다. 유아숲체험은 어차피 이 정보를 받아야 하므로, 폼을 만들면 본인확인은 잉여가 됩니다.

**③ 어뷰징 방어 — 전화번호로 대체됩니다.** 계정을 여러 개 만들어 쿠폰을 중복 수령하는 것을 막으려면 사람 단위 식별이 필요한데, 여기 쓰이는 값은 CI가 아니라 **DI(중복가입확인정보)**입니다. 다만 우리는 알림톡 발송 때문에 **전화번호를 어차피 확보**하므로(15-4), 번호 중복 체크로 대량 어뷰징이 걸립니다. 번호를 새로 만들려면 유심을 사야 해서 비용이 듭니다. CI/DI도 가족 명의를 빌리면 뚫리므로 완벽한 수단은 아닙니다.

**법적으로도 필수가 아닙니다.** 본인확인이 법으로 요구되는 것은 주류처럼 성인/미성년 구분이 필요한 상품, 금융·통신 계약 등입니다. 프로그램 예약은 해당하지 않습니다. 벤치마킹한 6개 플랫폼(숨고·마인드카페·프립·솜씨당·탈잉·클래스101) 조사에서도 **공급자 검증 사례는 다수 확인됐지만 소비자 본인확인 요구 사례는 발견되지 않았습니다.**

> **사용자가 결제할 때 겪는 "인증"은 대부분 본인확인이 아닙니다.** 카드사 앱 인증·간편결제 비밀번호는 "이 카드가 당신 것인지"를 카드사가 확인하는 절차이고, 토스페이먼츠 결제창이 알아서 띄웁니다. **우리가 만들 것도 비용을 낼 것도 없습니다.**

#### 재검토 트리거 (이 중 하나가 발생하면 다시 논의)

- **전화번호 중복 체크로 막히지 않는 어뷰징이 실제로 관측될 때** (예: 유심 여러 개를 동원한 조직적 쿠폰 수령)
- **성인 대상 상품이 생길 때** — 이 경우 본인확인은 법적 의무입니다
- **바우처 연계가 실제로 붙을 때** — 취약계층 자격 확인은 별도 체계지만 실명 대조가 필요해질 수 있습니다
- **아동·청소년 대상 프로그램에 법정 요건이 확인될 때** (13번 P2)

#### 공급자 본인확인은 유지합니다

정산 계좌의 예금주 이름과 가입자 실명이 같은지, 제출한 자격증의 이름과 일치하는지 대조해야 합니다. 관리자 수기 심사(12-1)가 결국 이름 대조 작업인데 실명이 없으면 대조할 기준 자체가 없습니다. **여기에는 대안이 없습니다.**

### 15-2. 용어 정리 — "문자인증"은 두 가지를 뜻합니다

v10까지 문서에 "문자인증"이라고만 적혀 있었는데, 국내에서 이 말은 서로 다른 두 가지를 가리킵니다. 비용도 법적 효력도 다르므로 이 문서에서는 아래 용어로 구분합니다.

| 용어 | 확인 범위 | 얻는 정보 |
|---|---|---|
| **SMS OTP** (번호 소유 확인) | "이 번호를 지금 쓰는 사람이 맞다" | 전화번호뿐 |
| **휴대폰 본인확인** | "이 사람이 누구인지" — 통신사 가입정보 대조 | 실명·생년월일·성별·CI/DI |

**우리가 채택하는 것은 휴대폰 본인확인입니다.** SMS OTP로는 공급자 계좌 명의 대조도, 미성년자 판별도 불가능합니다.

### 15-3. 벤더 — KG이니시스 통합 본인인증 (포트원 경유)

> **정정 이력:** 최초 검토에서는 다날 휴대폰 본인확인(월 정액)을 채택했으나, 초기 사용량을 대입해보니 **월 정액제가 초기 규모에 명백히 불리**해 KG이니시스 통합 본인인증으로 변경했습니다. 당시 다날을 고른 근거 세 가지 중 두 가지가 사실과 달랐던 점도 함께 기록합니다.

| 후보 | 요금 구조 | 판단 |
|---|---|---|
| **KG이니시스 통합 본인인증** (포트원 경유) | **월 기본료 없음.** 인증 성공 건당 약 35~40원(VAT 별도). 최초 가입비·설치비 약 3~5만원(제휴 플랫폼에 따라 상이, 포트원 경유 시 면제 가능) | **채택** |
| 다날 휴대폰 본인확인 (포트원 경유) | 월 정액 5만원/1,200건 ~ 30만원/7,200건. 포트원 경유 시 가입비 면제 | 보류 — 월 1,250건을 넘어서면 재검토 |
| Firebase Auth 전화번호 인증 | 건당 약 $0.01~$0.06(한국은 상단 추정). 2024년 9월부터 Blaze 필수, 일 10건까지만 무료 | 제외 — **SMS OTP라 실명을 못 얻음**(15-2) |

**손익분기는 월 1,250건입니다.** `50,000원 ÷ 40원 = 1,250`. 이보다 적으면 종량제(KG이니시스)가, 많으면 정액제(다날)가 쌉니다.

| 월 본인확인 건수 | KG이니시스 | 다날 |
|---|---|---|
| 50건 | **2,000원** | 50,000원 |
| 100건 | **4,000원** | 50,000원 |
| 500건 | **20,000원** | 50,000원 |
| 1,250건 | 50,000원 | 50,000원 |
| 2,000건 | 80,000원 | **50,000원** |

**(v12) 우리 예상 건수는 월 10건 미만입니다.** 소비자 본인확인을 제외했으므로(15-1) 본인확인은 **공급자가 등록할 때만** 발생합니다. 1단계 공급자 목표가 50~100명이고 그마저 1회성이라, **1년 전체를 합쳐도 100~200건 수준**입니다.

| 구분 | 연간 예상 |
|---|---|
| 본인확인 건수 | 100~200건 (공급자 등록 1회성) |
| KG이니시스 종량제 | **4,000~8,000원** |
| 다날 정액제 | 600,000원 |

이 규모에서는 **가입비 3~5만원이 오히려 연간 이용료보다 큽니다.** 계약 시 가입비 면제 협의를 우선하세요.

**부수적 이점:** 통합 본인인증은 PASS·토스·네이버·카카오·은행 인증서 등을 한 창에서 고르게 해줍니다. 휴대폰 인증 하나만 있는 것보다 이탈이 적고, 이미 카카오·네이버로 가입한 사용자에게는 같은 앱으로 인증하는 흐름이 자연스럽습니다.

**최초 검토에서 틀렸던 근거 두 가지 (기록용):**

1. **"포트원 경유라 계약 창구가 하나로 줄어든다"** — 다날만의 장점이 아닙니다. 포트원은 휴대폰 본인인증에 다날, **통합 본인인증에 KG이니시스**를 지원합니다. 둘 다 포트원 경유이고 가입 절차도 동일합니다.
2. **"CI를 받아 중복 가입을 막을 수 있다"** — 통합 본인인증도 본인확인기관을 거치므로 CI/DI를 동일하게 받습니다. 차이가 없습니다.

세 번째 근거였던 "정액제라 비용 예측이 쉽다"는 사실이지만, 예측 가능성을 얻는 대가가 **10배 이상의 비용**이라 초기 단계에서는 장점이 아닙니다.

> **계약 전 확인 필요:** 위 단가는 공개 자료 기준(포트원 블로그 2024.12 등)이며 제휴 조건에 따라 달라집니다. 가입비 면제 여부, 건당 단가(VAT 포함/별도), 최소 사용료 유무를 견적으로 확정한 뒤 계약하세요.

> **전환 시점:** 월 본인확인이 1,250건을 안정적으로 넘기면 다날 정액제로 전환을 검토합니다. 소비자 본인확인을 제외한 현 설계에서는 **당분간 도달할 가능성이 없습니다.** 둘 다 포트원 경유라 교체 부담이 크지 않지만, 연동 코드가 완전히 동일하지는 않으므로 약간의 작업은 필요합니다.

> **(v12) 호출량:** 소비자는 본인확인을 전혀 거치지 않습니다. 따라서 사용량은 **신규 공급자 수에만 비례**하며 소비자 트래픽과 완전히 무관합니다.

### 15-4. 전화번호 확보 경로 (알림톡 발송에 필수)

예약 확정·일정 변경·문의 답변 알림이 전부 알림톡·SMS로 나가므로 **전화번호는 반드시 확보해야 합니다.** 소셜 가입만으로 끝나는 소비자도 예외가 아닙니다.

1. **1순위 — 소셜에서 제공받기.** 카카오·네이버 모두 제공 항목에 휴대전화번호가 있습니다. 다만 **양쪽 다 사전 심사를 통과해야** 실제로 값이 넘어옵니다(네이버는 사전 검수, 카카오는 비즈 앱 전환 + 동의항목 심사). 심사를 통과해 필수 동의로 지정해도 **사용자 계정에 번호가 등록돼 있지 않으면 빈 값**으로 옵니다.
2. **2순위 — 예약 시점에 직접 입력받기.** 소셜 심사가 끝나지 않았거나, 전화번호 항목이 거부되거나, 계정에 번호가 없으면 첫 예약 화면에서 번호를 받습니다.
3. **공급자**는 본인확인 과정에서 번호가 확보되므로 별도 입력이 불필요합니다.

> **(v14 실측 갱신 — 2026-08-14) 네이버는 전화번호를 실제로 주고 있습니다.** 검수 통과 후 실제 로그인으로 확인했고, `users.phone`이 E.164로 정상 저장됐습니다. 따라서 아래 "2순위 먼저" 지침은 **네이버 사용자에 한해 급하지 않습니다.** 다만 다음 세 경우에는 여전히 번호가 비므로 예약 기능을 만들 때 함께 구현해야 합니다 — ① 카카오 사용자(심사 미신청) ② 네이버 계정에 번호가 등록돼 있지 않은 사용자 ③ 이미 다른 계정이 선점한 번호(2-14 정책상 `phone`을 비워 둠).

> **(v14) 구현 순서 주의 — 2순위를 1순위보다 먼저 만듭니다.** 위 순서는 값을 확보하는 **우선순위**이지 구현 순서가 아닙니다. 심사가 끝나기 전에는 소셜에서 번호가 **한 건도 오지 않으므로**, 1순위만 믿고 만들면 오픈 초기에 알림톡 발송 대상이 통째로 비어 있게 됩니다. 예약 화면의 번호 입력 경로를 먼저 완성해두고, 심사가 끝나면 1순위가 자동으로 얹히는 구조로 갑니다(재로그인 동기화 규칙에 따라 **우리 쪽 값이 비어 있을 때만** 채웁니다).

> **(v12) 전화번호는 어뷰징 방어 수단도 겸합니다.** 향후 쿠폰·프로모션을 도입할 때, 같은 번호로 재가입·중복 수령을 막는 것으로 본인확인 없이도 대량 어뷰징을 차단할 수 있습니다(15-1 ③). 이를 위해 **번호는 정규화(하이픈 제거, 국가번호 통일)해서 저장하고 `users`에 유니크 제약에 준하는 검사를 서버에서 수행**합니다.

### 15-5. 화면 변경 사항

- 로그인 모달(`src/components/LoginDialog.tsx`)에서 **휴대폰 번호 입력·인증번호 받기 UI를 제거**하고 카카오·네이버 버튼만 남깁니다.
- **(v12)** 결제 흐름에는 본인확인을 넣지 않습니다. 본인확인은 **공급자 등록 흐름에만** 배치합니다.
- 예약 화면에 참가자 정보 입력 폼을 신설합니다 — 15-6 참고.

### 15-6. 예약 폼 — 참가자 정보 (v12 신규)

소비자 본인확인을 제외한 대신, **아동 안전과 사고 대응은 예약 폼에서 확보**합니다. 본인확인 API로는 얻을 수 없는 정보들이므로 이 폼이 실질적인 안전장치입니다.

| 항목 | 필수 여부 | 비고 |
|---|---|---|
| 참가자 이름 | 필수 | 인원수만큼 입력 |
| 참가자 생년월일 | **아동 대상 프로그램은 필수** | `YYYY-MM-DD`. 프로그램의 대상연령 범위와 서버에서 대조 — 판정 기준일은 아래 참고 **(v13: 「연령 또는 생년」에서 생년월일로 단일화)** |
| 보호자 이름·연락처 | 아동 대상 프로그램은 필수 | 예약자와 다를 수 있음 |
| 비상 연락처 | 필수 | 예약자 번호와 달라도 됨 |
| 특이사항 | 선택 | 알레르기·지병·복용약 — 공급자에게 전달 |

**아동 대상 프로그램 판별 (v13 확정):** `programs.requiresChildInfo`(서버 파생 불리언, 2-3)로 판별합니다. 산출식은 `targetAgeMax != null && targetAgeMax <= 13` 이거나 `category == '유아숲체험'`이면 true입니다. `targetAgeMin`/`targetAgeMax` 필드는 v13에서 2-3에 정식 추가됐고 13번 P1입니다.

> **(v13 보완) 연령 제한이 없는 프로그램의 구멍.** `targetAgeMin`·`targetAgeMax`가 둘 다 null이면 `requiresChildInfo`가 false가 되어, **아이가 참가해도 연령·보호자·비상연락처를 받지 않습니다.** "소비자 본인확인을 뺀 대신 예약 폼으로 아동 안전을 확보한다"(15-1)는 근거가 이 구간에서 무너집니다. → **참가자 중 한 명이라도 `age < 14`로 입력되면 보호자·비상연락처를 그 자리에서 필수로 승격**합니다. 서버도 같은 조건으로 검증합니다.

> **(v13 보완) 연령 입력 단위와 판정 기준일.** 「참가자 연령(또는 생년)」처럼 두 가지를 허용하면 만 나이가 ±1세 흔들려, `targetAgeMax=6`인 프로그램에 같은 2019년생이 예약자에 따라 통과하거나 거부됩니다. → **생년월일(YYYY-MM-DD)로 단일화**하고, 만 나이 판정 기준일은 **회차 진행일**(`schedules.startAt`, `open` 타입은 `bookings.negotiatedDate`)로 고정합니다.

> **개인정보 최소수집:** 특이사항에는 건강 정보가 들어올 수 있어 **민감정보에 준해 취급**합니다. 프로그램 종료 후 보관 기간을 정해 파기하고, 공급자에게는 해당 예약 건에 한해서만 노출합니다. 약관·개인정보 처리방침에 수집 항목과 목적을 명시해야 합니다.

### 15-7. 소셜 앱 등록 값 (v14 신규 — 2026-08-14 네이버 검수 통과)

**비밀값이 아닙니다.** 콜백 URL과 서비스 URL은 브라우저 주소창에 그대로 드러나는 값이라 이 문서에 적어둡니다. Client Secret은 여기에도, 코드에도, 커밋에도 적지 않습니다 — 보관 위치는 `functions/README.md`.

| 항목 | 값 |
|---|---|
| 서비스 URL | `https://foom.kr` |
| 네이버 콜백 URL (로컬) | `http://localhost:5173/auth/naver/callback` |
| 네이버 콜백 URL (운영) | `https://foom.kr/auth/naver/callback` |
| 네이버 제공 항목 검수 | **통과** (휴대전화번호 필수 제공 항목 포함) |
| **네이버 앱 상태** | **개발 중** — 아래 주의사항 참고 |
| 카카오 | 미신청 — 비즈 앱 전환 + 동의항목 심사 필요 |

> **⚠️ 앱이 「개발 중」 상태라 아무 아이디로나 로그인되지 않습니다.** 개발자센터에 **테스트 멤버로 등록한 네이버 아이디만** 로그인됩니다. 등록되지 않은 계정은 네이버 화면에서 *"foom은 개발 중 상태입니다. 개발 중 상태에서는 등록된 아이디만 로그인할 수 있습니다"* 를 받고 우리 화면까지 오지 않습니다. **이건 우리 코드 문제가 아니므로 디버깅하지 마세요** — 팀원이 늘면 그 사람의 아이디를 개발자센터에 추가해야 합니다.
>
> 참고로 이 문구가 떴다는 것은 **연동이 정상이라는 증거**입니다. Client ID가 틀리면 "존재하지 않는 애플리케이션", 콜백 URL이 등록값과 다르면 "잘못된 리다이렉트 URI"가 대신 나옵니다.
>
> **「서비스 적용」 전환은 배포 이후입니다.** 서비스 URL(`https://foom.kr`)이 실제로 열려 있어야 심사가 통과하는데 아직 배포 전입니다.

> **네이버 단체·기업 아이디로는 로그인되지 않습니다.** 소속 관리자가 외부 서비스 연동을 막아둘 수 있고, 그 경우 *"관리자에게 문의하세요"* 계열 문구가 뜹니다. **개인 네이버 아이디로 테스트**하세요. 우리 쪽에서 풀 수 있는 문제가 아닙니다.

> **다른 기기(휴대폰)에서는 로컬 테스트가 불가능합니다.** 콜백이 `http://localhost:5173`으로 등록돼 있어 휴대폰의 `localhost`는 그 폰 자신을 가리킵니다. QR로 접속해도 로그인은 되지 않습니다 — **개발 서버를 띄운 PC의 브라우저에서** 테스트하세요.

> **콜백 목적지는 프론트엔드 라우트입니다.** 함수(`/api/...`)가 아니라 SPA 화면입니다. 따라서 흐름은 **네이버 → 프론트 콜백 화면(인가코드 수신) → 프론트가 코드를 서버로 전달 → 서버가 토큰 교환·프로필 조회·Custom Token 발급** 순서가 됩니다. 클라이언트가 서버로 넘기는 것은 **인가코드와 state뿐**이고 이름·이메일·전화번호는 넘기지 않으므로, "프로필 값은 서버가 직접 조회한 것만 쓴다"는 v14 원칙(2-1)이 그대로 지켜집니다.

> **`state` 파라미터는 반드시 씁니다.** 인가 요청 때 난수를 만들어 보관하고 콜백에서 받은 값과 대조합니다. 빠뜨리면 CSRF로 **다른 사람의 소셜 계정에 우리 세션을 붙이는** 공격이 가능합니다.

> **로컬 포트는 5173으로 고정합니다.** 콜백 URL은 등록된 문자열과 **완전히 일치**해야 합니다. Vite는 5173이 사용 중이면 조용히 5174로 옮겨가는데, 그러면 로그인만 실패하고 원인은 화면에 안 나옵니다. → `vite.config.ts`에 `strictPort: true`를 넣어 포트를 못 잡으면 **서버가 아예 안 뜨게** 했습니다. 같은 이유로 `127.0.0.1:5173`이 아니라 **`localhost:5173`으로 접속**해야 합니다(등록된 문자열이 `localhost`).

### 15-8. ⚠️ 임시 공급자 지정 경로 (v14 신규 — 정식 오픈 전 반드시 제거)

**이것은 15-1과 다른 임시 우회로입니다.** 정식 공급자 등록은 **휴대폰 본인확인 필수 + 자격증 제출 → 관리자 심사**인데(15-1), 본인확인 벤더(KG이니시스/포트원, 15-3)가 **아직 계약 전**입니다. 공급자가 없으면 프로그램도 만들 수 없어 개발 자체가 막히므로, 그 사이를 메우는 임시 경로를 둡니다.

| 항목 | 내용 |
|---|---|
| 경로 | `npm run grant-provider -- --uid <uid>` — **Admin SDK 스크립트만** |
| 하는 일 | `users.role='provider'` + `providerProfiles/{uid}` 공개 문서 + `private/profile` 생성 |
| 남는 상태 | `approvalStatus='pending'`, 공개 프로필 `verified=false` |
| 화면·API | **만들지 않습니다** |

**왜 스크립트로만 두는가.** 관리자 지정(12-3)과 같은 이유입니다 — 화면이나 API로 열면 **누구나 공급자가 되어 심사 없이 프로그램을 올릴 수 있습니다.** 권한 상승 경로를 스스로 만드는 셈입니다.

**왜 `approved`가 아니라 `pending`인가.** 심사를 거치지 않은 계정을 승인된 것처럼 기록하면, 나중에 **어느 계정이 실제로 심사를 통과했는지 구분할 수 없게 됩니다.** `verified=false`이므로 화면의 "인증" 배지도 붙지 않습니다.

> **정식 오픈 전 체크리스트 (이걸 안 하면 무자격자가 프로그램을 팔게 됩니다):**
> 1. `POST /auth/provider/apply` — 본인확인 + 자격증 제출 구현
> 2. `POST /admin/providers/{id}/approve` — 심사로 `approvalStatus`·`verified` 전환
> 3. **이 스크립트로 만들어진 계정 전부를 재심사** (`approvalStatus='pending'`으로 찾을 수 있습니다)
> 4. `grant-provider` 스크립트 삭제

### 15-9. 공급자 등록 화면 — 「안내만」으로 확정 (v15 신규, 2026-08-18)

`/provider/apply` 화면을 **신청 폼이 아니라 안내 화면**으로 만들었습니다. 헤더의 「전문가로 활동하기」와 푸터의 「전문가 가입 안내」가 여기로 갑니다.

**왜 신청 기능을 만들지 않았는가.** 정식 절차(15-1)의 첫 단계가 휴대폰 본인확인인데 벤더가 아직 계약 전이고(15-3), 자격증 이미지를 올릴 Storage도 설정돼 있지 않습니다. 두 조각이 없는 상태에서 폼부터 만들면 **"관리자가 무엇을 보고 승인하는가"가 정해지지 않은 채 필드를 정하게 됩니다.** 자격 부여는 그동안 `grant-provider` 스크립트가 계속 담당합니다(15-8).

**함께 해결된 것:** 그 전에는 헤더·푸터가 `/programs/new`로 직결돼 있어서, 공급자가 아닌 사용자가 **등록 폼을 다 채운 뒤에야** `permission-denied`로 거부됐습니다. 안내 화면을 거치게 하고, 등록 화면 자체에도 `GET /users/me`로 역할을 먼저 확인해 폼 대신 안내를 보여주도록 했습니다.

화면이 상태에 따라 다르게 보입니다 — 비로그인이면 로그인 안내, 소비자면 "온라인 신청 준비 중 + 문의 안내"와 함께 자기 uid(운영자가 스크립트로 찾을 값), 공급자면 심사 상태(`pending`/`approved`/`rejected`)와 반려 사유, 그리고 프로그램 등록 버튼입니다.

## 16. 날씨 API 연동 설계 (v11 신규)

홈 프로모 카드(9-7 ②)뿐 아니라 **프로그램 상세와 회차별로도 날씨를 표시**하기로 했습니다. 화면이 늘어도 서버 함수는 `GET /external/weather` 하나를 공유하므로 구현량은 늘지 않지만, 호출량이 늘면 비용과 성능에 영향이 생기므로 아래 전략을 미리 정해둡니다.

### 16-1. 캐싱 — 이것만 하면 비용이 사실상 0원입니다

**기상청 단기예보는 하루 8번만 발표됩니다**(02·05·08·11·14·17·20·23시). 그 사이에는 몇 번을 물어봐도 같은 값이 돌아오므로, **3시간 단위로 한 번만 받아 저장하고 재사용**합니다.

또한 기상청은 좌표를 **5km 격자(nx, ny)**로 처리하므로, 같은 지역 프로그램들은 **격자 하나의 캐시를 공유**합니다.

| | 캐시 없음 | 캐시 적용 |
|---|---|---|
| 기상청 호출 | 방문 1,000명 × 상세 3건 = **일 3,000건** | 격자 50개 × 8회 = **일 400건** |
| 무료 한도(일 10,000건) 대비 | 30% | 4% |

캐시를 적용하면 **호출 수가 방문자 수가 아니라 격자 수에 비례**하므로, 사용자가 늘어도 비용이 늘지 않습니다.

**저장 위치:** Firestore `weatherCache` 컬렉션. 문서 ID는 `{nx}_{ny}_{발표시각}` 형태로 두고 TTL 3시간. 보안규칙은 클라이언트 읽기 허용·쓰기 금지(서버 전용)로 둡니다. Functions 인스턴스 메모리 캐시는 인스턴스가 재시작되면 날아가므로 보조 수단으로만 씁니다.

**파이어베이스 비용:** Functions 월 200만 호출 무료 범위(이 수준이면 월 9만 건), Firestore 캐시 읽기 일 3,000건(무료 한도 일 5만) — **모두 무료 범위 안**입니다.

### 16-2. 예보 기간 한계와 화면 처리

**단기예보는 최대 3~4일 뒤까지만 제공됩니다.** 중기예보(3~10일)는 별도 API이고 오전/오후 단위라 훨씬 성깁니다.

우리 프로그램에는 한 달 뒤 회차도 있으므로, 예보가 없는 구간의 처리 규칙을 정합니다.

| 진행일까지 남은 기간 | 표시 |
|---|---|
| 3~4일 이내 | 단기예보 표시 (기온·하늘상태·강수확률·특보) |
| 그 이후 | **"진행일이 가까워지면 예보가 표시됩니다"** 안내 문구 |

중기예보 연동은 1차 오픈 범위에 넣지 않습니다. 한 달 뒤 날씨를 보여주는 것은 사용자에게 의미가 없고, 오히려 부정확한 정보로 오해를 부를 수 있습니다.

### 16-3. 구현 시 주의

- **기상청 API는 반드시 Cloud Functions를 경유합니다.** 프론트에서 직접 호출하면 API 키가 노출되고, 기상청 서버가 CORS를 막아 요청 자체가 거부됩니다.
- **좌표 → 격자 변환(람베르트 도법)을 서버에 구현해야 합니다.** 기상청은 위경도가 아니라 자체 격자 좌표를 받습니다.
- **날씨는 화면 렌더링을 막지 않게 비동기로 불러옵니다.** 자리표시자를 먼저 그리고 데이터가 오면 채웁니다. 응답 자체는 수 KB로 가볍습니다.
- **날씨는 참고용이며 환불정책·자동취소와 무관합니다**(14-1). 우천 시 진행 여부는 공급자 재량이라는 원칙은 그대로입니다.

## 17. 검색 필터 시스템 (v13 신규)

프로그램 찾기 화면의 필터입니다. 프립을 참고해 **화면을 먼저 프로토타입으로 확정한 뒤 필요한 필드를 역산**했습니다. 이 순서 덕분에 정렬 3종에 기준 필드가 없다는 사실을 착수 전에 발견했습니다(17-3).

### 17-1. 필터를 클라이언트 Firestore 쿼리로 만들지 않습니다

**Firestore는 쿼리 하나를 논리곱 정규형(DNF) 기준 논리합 30개로 제한합니다.** 다중선택 필터는 논리합으로 펼쳐지므로 곱셈으로 늘어납니다.

| 조합 | 논리합 개수 | 결과 |
|---|---|---|
| 카테고리 5개 선택 | 5 | 통과 |
| 카테고리 5개 × 대상연령 6개 | 30 | **상한에 정확히 닿음** |
| 위 조합 + 기간 31일 | 930 | **불가능** |

여기에 두 번째 문제가 겹칩니다 — **필터 조합마다 복합 인덱스가 필요합니다.** 필터 7종과 정렬 6종을 모두 조합하면 인덱스를 수십 개 만들어 관리해야 하고, 필터를 하나 추가할 때마다 인덱스가 배로 늘어납니다.

**→ 검색을 `GET /programs/search` Cloud Function 하나로 모으고, 그 함수는 Firestore 문서 딱 한 개만 읽습니다.**

`aggregates/searchIndex` 문서에 게시 중 프로그램의 **필터·정렬에 쓰는 필드만 추린 사본**을 배열로 담아둡니다. 검색 함수는 이 문서 1건을 읽어 메모리에서 필터·정렬·페이지네이션을 모두 처리합니다.

| 항목 | 방식 |
|---|---|
| 데이터 소스 | `aggregates/searchIndex` **문서 1건** — 게시 프로그램의 필터·정렬 필드 사본 배열 |
| 필터·정렬 | 전부 함수 메모리에서 처리 — 논리합 30개 제한과 인덱스 행렬 문제가 함께 사라짐 |
| 갱신 | `scheduledFn: rebuildSearchIndex`(10분 주기) + 프로그램 승인 시 즉시 1회 |
| 읽기 비용 | 검색 요청당 **1 읽기**(캐시 미스 시). TTL 5분 인메모리 캐시를 얹으면 그 이하 |
| 문서 크기 | 프로그램 1건당 약 300B × 200건 ≈ 60KB. Firestore 문서 상한 1MiB의 6% |
| 대가 | 게시 직후 최대 10분간 검색에 안 잡힘 → 승인 시 즉시 갱신을 함께 호출해 수초로 줄입니다 |

> **(v13 정정) 원래 초안은 "게시 프로그램 전량을 함수 메모리에 TTL 5분으로 캐시, 웜 상태 읽기 0건"이었고 비용을 "일 2,400 읽기"로 적었습니다. 두 군데가 틀렸습니다.**
> ① **산수 오류** — TTL 5분이면 인스턴스 1개당 시간당 12회 갱신 × 200건 = 시간당 2,400 읽기이고, 하루로는 **57,600 읽기**입니다. 무료 쿼터(5만/일)를 인스턴스 하나로 이미 넘깁니다.
> ② **Cloud Functions는 인스턴스가 여러 개입니다.** 인스턴스마다 캐시와 TTL 시작점이 따로라 위 수치에 동시 인스턴스 수가 곱해집니다. 게다가 인스턴스별로 캐시 시점이 달라 **새로고침할 때마다 결과가 나타났다 사라지는 현상**이 생깁니다 — "5분 후 반영"으로 설명되지 않는 증상입니다.
> → 갱신 단위를 **문서 200건 조회에서 집계 문서 1건 조회로** 바꿔 해결했습니다. 모든 인스턴스가 같은 문서를 읽으므로 결과가 흔들리지 않고, 읽기량이 인스턴스 수와 무관해집니다.

> **언제 이 구조를 버려야 하나:** 문서 상한 1MiB가 곧 정원입니다 — 프로그램 1건당 300B면 **약 3,000건**에서 한계에 닿습니다. 그 전에(2,000건 즈음) 전용 검색엔진(Typesense·Algolia 등)으로 교체합니다. **프론트가 이 엔드포인트 하나만 호출하도록 만들어 두면 교체 범위가 함수 내부로 국한됩니다.** 프론트에서 Firestore를 직접 쿼리하게 만들면 그때 전면 수정이 됩니다.

### 17-2. 기간(날짜) 필터 — 가장 어려운 부분

날짜는 `programs`가 아니라 하위 `schedules`에 있습니다. **Firestore에는 조인이 없으므로** "8/15~8/18에 회차가 있는 프로그램"을 한 번의 쿼리로 찾을 수 없습니다. 세 가지 방법을 비교했습니다.

| 방법 | 내용 | 판단 |
|---|---|---|
| A. 회차 먼저 조회 | collectionGroup으로 기간 내 `schedules`를 찾고 `programId`를 모아 프로그램을 조회 | **미채택** — 인기 프로그램 하나가 회차를 수십 개 갖고 있어 결과 개수를 예측할 수 없고, 프로그램 조회의 `in` 30건 제한 때문에 페이지네이션이 깨짐 |
| B. 기간 겹침 판정 | `nextScheduleAt <= 종료일 && lastScheduleAt >= 시작일` | **부정확** — 8/1과 9/30에만 회차가 있는 프로그램이 8/20~8/25 검색에 잡힘. 1차 후보 좁히기에만 사용 |
| C. 날짜 배열 비정규화 | 프로그램 문서에 미래 회차 날짜 목록(`scheduleDates`)을 문자열 배열로 보관하고 교집합 검사 | **채택** |

**C의 유지 방법이 이 설계의 핵심 리스크입니다.** `schedules`는 여러 경로에서 바뀝니다 — 템플릿 배치 생성, 공급자 수동 추가·삭제, 정원 소진, `markBookingsCompleted`로 과거가 되는 경우. 갱신을 각 경로에 흩어 놓으면 한 곳을 빠뜨려 **"달력에 점은 있는데 예약이 안 되는"** 불일치가 생깁니다.

→ **`syncProgramScheduleDates(programId)` 단일 함수로 묶고, 회차를 만들거나 지우는 모든 경로가 이 함수만 호출합니다.** 이 함수가 `scheduleDates`·`nextScheduleAt`·`lastScheduleAt`·`aggregates/scheduleCalendar`를 한꺼번에 갱신합니다.

**기간 선택 상한: 오늘 ~ +90일, 연속 최대 31일.**

- **+90일**은 `scheduleTemplates` 롤링 윈도우와 같은 값입니다(2-4에서 8주 → 90일로 통일). 캘린더가 회차 생성 범위보다 먼 달을 보여주면 결과가 0건인 게 정상인데 사용자는 고장으로 읽습니다.
- **31일**은 결과 집합과 응답 크기를 예측 가능하게 유지하기 위한 값입니다. UI에서 31일을 넘겨 고르면 종료일을 자동으로 당기고 안내 문구를 띄웁니다.

**시간이 지나는 것도 갱신 트리거입니다 (v13 정정 — 처음에 빠뜨렸던 경로).** 위에 적은 트리거(템플릿 배치, 수동 추가·삭제, 정원 소진, `markBookingsCompleted`)에는 **"날짜가 그냥 지남"이 없습니다.** 예약이 0건인 회차는 날짜가 지나도 `markBookingsCompleted`가 건드릴 예약이 없어 sync가 돌지 않고, `single`·`series` 프로그램은 롤링 윈도우 배치 대상도 아닙니다. 그러면 `nextScheduleAt`이 **과거 시각으로 영구 고정**되어 "빠른 날짜순" 최상단에 지난 회차가 뜨고, `scheduleDates`에 남은 과거 날짜가 캘린더 점으로 계속 찍힙니다 — 사용자는 점을 보고 눌렀는데 그 날짜가 클릭 불가(17-4 ④)인 상황을 겪습니다.
→ `rebuildSearchIndex`(10분 주기)가 매번 **오늘 이전 날짜를 걷어내고** `nextScheduleAt`이 과거인 프로그램의 sync를 다시 돌립니다.

**상시모집(`open`) 처리 — 기간 필터의 예외입니다.** `open` 타입은 `schedules`가 없어서 기간 필터로는 전부 탈락하는데, 실제로는 "그 기간에 협의가 가능한" 프로그램입니다. → **`availableFrom`~`availableUntil`이 선택 기간과 겹치면 결과에 포함**하고, 목록 카드에 「날짜 협의」 배지를 붙여 구분합니다. 결과 상단에 "상시모집 N개는 날짜를 협의하는 방식이라 기간과 무관하게 함께 표시됩니다"를 노출합니다 — 안 그러면 8월로 검색했는데 날짜가 없는 카드가 섞여 있는 것으로 보입니다.

> **(v13 정정) 이 예외는 Firestore 쿼리로는 만들 수 없었습니다.** 초안은 1차 좁히기를 `status + sido + nextScheduleAt` 쿼리로 하려 했는데, **Firestore는 인덱스에 쓰인 필드에 값이 없는 문서를 아예 색인하지 않습니다.** `open`은 회차가 없어 `nextScheduleAt`이 없거나 null이므로, 그 쿼리에서 상시모집 프로그램이 **100% 누락**됩니다. null을 명시해도 부등호 필터(`>= 오늘`)에는 걸리지 않고, 반대로 부등호 없이 정렬만 하면 **null인 프로그램이 모든 날짜 정렬의 최상단**을 차지합니다.
> → 17-1에서 검색 데이터 소스를 집계 문서 1건으로 바꾸면서 이 문제가 함께 없어졌습니다. `open`도 집계에 포함되고 판정은 메모리에서 하기 때문입니다. **다만 `nextScheduleAt`/`lastScheduleAt`은 `open`에서도 명시적 `null`로 기록합니다**(2-3) — 다른 쿼리에서 같은 함정을 다시 밟지 않기 위해서입니다.

### 17-3. 필터 항목 확정

| 항목 | 방식 | 대응 필드 | 비고 |
|---|---|---|---|
| 카테고리 | **다중 선택** 칩 | `category` | 「전체」는 배타적 — 개별 항목을 하나라도 고르면 전체가 해제되고, 전부 해제하면 전체로 되돌아옵니다 |
| 기간 | 캘린더 범위 선택(아래로 펼침) | `scheduleDates` | 17-2 |
| 대상 연령 | **다중 선택** | `targetAgeTags` | **「제한 없음(`all`)」 프로그램은 어떤 연령을 골라도 항상 포함합니다** — 제외하면 전연령 프로그램이 사라져 결과가 부자연스럽게 비어 보입니다. 태그 경계와 판정식은 2-3의 산출 기준표 |
| 가격 | 최소·최대 슬라이더 | `price` | 상한(30만원)은 "이상"으로 처리해 무한대로 봅니다 |
| 지역 | 단일 선택(8개 권역) | `sido` | 주소 문자열 검색이 아니라 코드 일치. **저장은 17개 시도, 화면은 8개 권역**이고 서버가 권역→시도 목록으로 펼쳐 판정합니다(4번 매핑표). 부산·대구 같은 광역시가 갈 곳이 없던 문제를 v13에서 정정 |
| 난이도 | 단일 선택 | `difficulty` | 라벨에 기준을 함께 노출 — 쉬움 1km 이하 / 보통 1~3km / 어려움 3km 이상 |
| 배리어프리 | 체크박스 | `barrierFree` | 용어 유지 + 도움말. 근거는 17-4 ③ |
| 우천 시 대체 | 체크박스 | `rainAlternative != 'none'` | 필터는 있냐/없냐로 받지만 **필드는 3값**입니다 — 「실내로 바꿔서 진행」과 「다른 날로 옮김」은 사용자에게 완전히 다른 이야기라 상세 화면에서 구분 표기해야 합니다 |

**정렬 6종 — 이 중 3종은 기준 필드가 없었습니다.**

| 정렬 | 기준 필드 | 상태 |
|---|---|---|
| 인기순(기본) | `bookingCount30d` | **v13 신규** — 없으면 "인기"의 정의 자체가 없습니다 |
| 신규순 | `publishedAt` | **v13 신규** — `createdAt`은 draft를 만든 시각이라 부적합 |
| 평점순 | `ratingAvg` | **v13 신규** (기존 13번 P2에서 승격) |
| 가까운거리순 | geohash + 거리 계산 | 7-1 지오쿼리 참고 |
| 낮은/높은 가격순 | `price` | 기존 필드 |

> `bookingCount30d`는 **일일 배치에서 재계산**합니다. 실시간일 필요가 없고, 예약마다 프로그램 문서를 쓰게 만들면 인기 프로그램에서 쓰기 경합이 생깁니다.

### 17-4. UX 확정 사항과 근거

**① 「내 주변」과 「지도로 보기」를 하나로 합쳤습니다.**
버튼이 둘이었지만 결국 둘 다 지도를 보여주는 동작이었습니다. 게다가 목록 화면에서 위치 권한을 먼저 물으면 **아직 지도를 볼지도 모르는 사용자에게 권한 팝업을 띄우는** 셈입니다. → 「지도로 보기」 하나만 두고, **지도 안 우하단에 「내 위치」 버튼**을 둡니다. 권한 요청은 그 버튼을 누른 순간에만 발생합니다.

**② 「7일 이내」 같은 기간 프리셋을 없앴습니다.**
초기 시안의 「7일 이내」는 **근거가 없는 값**이었습니다 — 환불정책(7일 전 전액환불)과 무관하고 팀에서 정한 바도 없습니다. 캘린더에서 직접 고르는 방식으로 교체했습니다.

**③ 「배리어프리」 용어를 유지하고 도움말을 붙였습니다.**
「무장애」가 우리말이지만 인지도가 낮고, 「배리어프리」는 관광·시설 분야에서 이미 통용되는 표기입니다. 용어를 바꾸는 대신 옆에 「?」를 두고 마우스를 올리면 설명이 뜨게 했습니다 — **대상연령·난이도·우천 시 대체에도 같은 방식**을 적용했습니다. 낯선 용어를 없애는 쪽과 정확한 용어를 쓰는 쪽 사이에서 후자를 택했습니다.

**④ 캘린더 표시 규칙 — 구현 시 그대로 따르세요.**

| 상태 | 표현 |
|---|---|
| 지난 날짜 | 빗금 + 아주 흐린 회색 + **클릭 불가**(`disabled` + `pointer-events:none` + 탭 이동 제외). 흐리게만 처리하면 눌러보고 반응이 없어 고장으로 읽힙니다 |
| 선택 기간 | 시작·종료일은 진한 브랜드 그린, 사이 날짜는 한 단계 밝은 그린으로 **끊김 없이 이어진 하나의 띠**. 기간 내 숫자는 전부 흰색 |
| 회차 있는 날 | 숫자 아래 작은 점 (출처는 17-5) |
| 오늘 | 초록 테두리 |

> **칸 사이 좌우 여백을 0으로 둬야 띠가 이어집니다.** 프로토타입에서 여백 2px 때문에 색이 조각나 보이는 문제가 실제로 발생했습니다. 위아래 여백만 남깁니다. 2개월을 나란히 보여주고 이동 범위는 오늘~+90일로 제한합니다.

**⑤ 필터 상태는 URL 쿼리로 유지합니다.**

```
/search?category=숲해설,산림치유&from=2026-08-15&to=2026-08-18&age=infant&region=gyeonggi&price=0-50000&level=easy&bf=1&rain=1&sort=popular&view=map
```

목록↔지도 전환, 상세 진입 후 뒤로가기, 링크 공유가 이 하나로 해결됩니다. 헤더 네비게이션이 이미 `/search?view=map`을 쓰고 있어 규칙이 일치합니다.

### 17-5. 캘린더의 「회차 있는 날」 점은 어디서 오는가

날짜마다 회차 존재 여부를 알아야 하는데, 달력을 열 때마다 전체 회차를 조회하면 읽기 비용이 큽니다. → **집계 문서 한 개**(`aggregates/scheduleCalendar`, 2-13)를 읽습니다. 읽기 1건으로 달력 전체가 칠해집니다.

**갱신은 `rebuildSearchIndex`(10분 주기 배치)가 통째로 다시 만드는 방식입니다 (v13 정정).** 초안은 `syncProgramScheduleDates`가 프로그램마다 이 문서를 갱신하는 구조였는데 두 가지 문제가 있었습니다.

| 문제 | 내용 |
|---|---|
| 쓰기 경합 | **모든 프로그램이 같은 한 문서를 씁니다.** 롤링 윈도우 배치가 매일 프로그램마다 회차를 만들며 sync를 호출하면 수백 건이 수초 안에 같은 문서를 두고 다툽니다. 단일 문서 지속 갱신률은 대략 초당 1회가 안전선이라 트랜잭션 재시도로 배치가 늘어지거나 갱신이 유실됩니다 |
| 멱등성 없음 | 값이 "그 날짜에 회차가 있는 **프로그램 수**"라 한 프로그램만 보고는 계산할 수 없습니다. `increment`로 처리하면 재시도로 두 번 실행될 때 **카운트가 부풀고 되돌릴 방법이 없습니다** |

→ **증분 갱신을 포기하고 전체 재생성**으로 바꿨습니다. 배치가 게시 프로그램의 `scheduleDates`를 모아 문서를 새로 쓰므로 몇 번 실행돼도 결과가 같고, 지난 날짜 키 제거도 같은 자리에서 처리됩니다. 문서에 `computedAt`을 함께 넣어 값이 얼마나 묵었는지 판단할 수 있게 합니다. 소실 시 복구는 `POST /admin/aggregates/rebuild`로 같은 로직을 수동 실행합니다(2-13이 요구한 재계산 경로).

> **알려진 한계 — 점은 "전체 프로그램 기준"입니다.** 카테고리를 좁힌 상태에서도 점은 그대로 보이므로 **"점이 있는데 결과가 0건"**인 상황이 생길 수 있습니다. 필터별 집계를 만들면 조합 폭발이 나므로 만들지 않고, 대신 결과 0건일 때 **"선택한 조건으로는 이 기간에 프로그램이 없습니다 — 카테고리를 넓혀보세요"**로 안내합니다. 점을 아예 없애는 선택지도 있었지만, 회차가 드문 초기에는 "언제 뭐가 있는지" 힌트가 없으면 사용자가 빈 날짜만 찍어보다 이탈합니다.

### 17-6. 보안·검증

- **`GET /programs/search`는 로그인 없이 호출됩니다.** Admin SDK는 보안규칙을 우회하므로 **함수 안에서 `status == 'published'`를 하드코딩**해야 합니다. 클라이언트가 보낸 status 파라미터는 무시합니다 — `draft`·`pending_review`가 검색에 노출되면 심사 절차 자체가 무의미해집니다.
- **정렬 필드를 문자열로 받아 그대로 쿼리에 넣지 마세요.** 화이트리스트(위 6종)로 검증합니다. 안 그러면 임의 필드 정렬로 비공개 필드의 순서를 통해 값을 추측할 수 있습니다.
- **기간 파라미터는 서버에서도 오늘~+90일, 최대 31일로 잘라냅니다.** 클라이언트 UI 제한만으로는 API 직접 호출을 막지 못합니다.
- `aggregates/*`는 읽기 공개·쓰기 서버 전용입니다(6-1). 개인이 역산되는 값은 담지 않습니다(2-13).

### 17-7. 작성 직후 교차검증에서 잡힌 결함 (v13 안에서 수정 완료)

17번 초안을 쓴 직후 별도 검토를 돌려 **8건**이 나왔습니다. 팀에 넘기기 전에 같은 v13 안에서 고쳤고, **같은 함정을 다시 밟지 않도록** 무엇이 틀렸는지 남깁니다.

| 심각도 | 무엇이 틀렸나 | 어떻게 됐나 |
|---|---|---|
| 치명 | `programs` 수정 규칙이 **금지목록** 방식이라, v13이 추가한 파생 필드 10여 개가 전부 클라이언트에 열려 있었음 | 허용목록으로 반전(6-1). 공급자가 `ratingAvg=5.0`·`bookingCount30d=999999`로 검색 1위를 차지할 수 있었음 |
| 치명 | 1차 좁히기를 `status + sido + nextScheduleAt` 인덱스 쿼리로 설계 → **상시모집(`open`)이 검색에서 100% 누락.** Firestore는 인덱스 필드에 값이 없는 문서를 색인하지 않음 | 검색 데이터 소스를 집계 문서 1건으로 변경(17-1). 인덱스 쿼리 자체를 없앰 |
| 치명 | 캐시 비용을 "일 2,400 읽기"로 적었으나 **실제로는 시간당 수치** — 하루 57,600 읽기로 무료 쿼터 초과. 다중 인스턴스도 고려하지 않았음 | 문서 1건 읽기 구조로 변경(17-1). 산수 오류를 그대로 기록 |
| 보통 | `scheduleDates` 갱신 트리거에 **"날짜가 그냥 지남"이 없었음** → 지난 회차가 캘린더에 영구 표시 | `rebuildSearchIndex`가 매 주기 과거 날짜를 정리(17-2) |
| 보통 | `aggregates/scheduleCalendar`를 프로그램마다 갱신하는 구조 → **단일 문서 쓰기 경합 + 멱등성 없음** | 배치 전체 재생성으로 변경(17-5) |
| 보통 | `targetAgeTags`의 **연령 경계가 정의되지 않았음** — 만 3~6세 프로그램의 태그가 무엇인지 구현자마다 달라짐 | 2-3에 산출 기준표와 판정식 추가 |
| 보통 | `region` enum에 **부산·대구·광주·대전·울산·세종 등 9개 시도가 없었음** → 매핑 실패로 지역 필터에서 누락 | `sido`(17개) 저장 + 화면은 8개 권역으로 묶음(4번 매핑표) |
| 보통 | `publishedAt`·`ratingAvg`·`bookingCount30d`의 **갱신 주체가 어디에도 없었음** → 정렬 3종이 동작하지 않음 | 5번에 `recalcProgramStats` 추가, 승인 API에 `publishedAt` 기록 명시 |

> **공통 원인은 하나입니다 — 화면을 먼저 확정하고 필드를 역산했더니, 그 필드를 "누가 쓰고 누가 막는지"를 같은 속도로 따라 정하지 못했습니다.** 필드를 추가할 때는 매번 네 가지를 함께 정해야 합니다: ① 누가 계산해 넣는가 ② 클라이언트가 못 쓰게 막았는가 ③ 값이 없거나 null인 문서는 어떻게 되는가 ④ 시간이 지나면 스테일해지는가.
- **`programs` 수정 규칙은 허용목록(화이트리스트) 방식입니다**(6-1). 파생 필드가 목록에 없으므로 클라이언트가 값을 넣으면 수정 전체가 거부됩니다. 필드를 새로 추가할 때 목록에 넣는 걸 잊으면 "저장이 안 되는 버그"로 드러나는데, 잊었을 때 보안 사고가 되는 금지목록보다 이쪽이 안전합니다.
- **입력값 범위 검증이 없으면 검색이 조용히 깨집니다.** `targetAgeMin > targetAgeMax`, 음수 `price`, `capacity < minCapacity`, enum 밖의 `difficulty`/`rainAlternative` 문자열이 그대로 저장되면 연령 태그 파생과 예약 검증(15-6)이 그 값을 신뢰합니다. 보안규칙과 `POST /programs` 양쪽에서 검증합니다(6-1).

## 18. 파일 저장(Firebase Storage) 설계 (v16 신규)

지금까지 이 문서에는 파일에 대한 설계가 없었습니다. "나중에 Storage로 교체한다"는 언급이 두 군데(9-7 ⑧, 13번 P1) 있을 뿐, **어느 경로에 두고 누가 읽을 수 있는지가 정해진 적이 없습니다.** 자격증처럼 공개되면 사고가 나는 파일이 걸려 있으므로, 콘솔에서 버킷을 만들기 전에 여기서 먼저 정합니다.

### 18-1. 무엇을 저장하는가 — 성격이 정반대인 두 종류

| 종류 | 담기는 것 | 공개 범위 | 쓰는 곳 |
|---|---|---|---|
| **프로그램 이미지** | 프로그램 대표 사진·상세 사진 | **전체 공개** — 비로그인 방문자도 봐야 함 | `programs.imageUrls`(2-3). 첫 장이 대표 썸네일 |
| **자격증 사본** | 산림복지전문가 자격증 이미지 | **관리자와 본인만** | `providerProfiles/{uid}/private/profile.certificateImageUrls`(2-2) |

**이 둘을 같은 상위 경로 아래 두지 않습니다.** 공개 경로와 비공개 경로를 최상위에서 갈라야 합니다 — 한 뿌리 아래 두면 "이 폴더는 공개"라는 규칙 한 줄이 실수로 자격증까지 열어버립니다. `providerProfiles`를 공개 문서와 `private` 하위 문서로 나눈 것과 같은 이유이고(2-2), 여기서는 문서가 아니라 **경로**로 나눕니다.

### 18-2. 버킷과 리전

- 기본 버킷 하나만 씁니다. 파일 종류는 경로로 나눕니다
- **리전은 `asia-northeast3`(서울)** — Cloud Functions와 같은 곳입니다
- **리전은 만든 뒤 바꿀 수 없습니다.** 버킷을 지우고 다시 만드는 것 외에 방법이 없으므로, 콘솔에서 생성할 때 이것만 확인하면 됩니다
- `firebase.json`에 `storage` 항목(규칙 파일 경로)을 추가해야 규칙이 배포됩니다 — 빠뜨리면 콘솔 기본 규칙이 그대로 남습니다

### 18-3. 경로 규칙

```
programs/{programId}/{fileId}          공개 읽기 / 소유 공급자만 쓰기
providerCertificates/{uid}/{fileId}    본인·관리자만 읽기 / 본인만 쓰기
```

- **경로에 소유자 식별자를 넣는 것이 규칙의 근거가 됩니다.** `{uid}`·`{programId}`가 경로에 있어야 "이 파일이 누구 것인지"를 규칙이 판단할 수 있습니다. 파일명만으로는 알 수 없습니다
- `{fileId}`는 클라이언트가 만드는 임의 문자열입니다. 원본 파일명을 그대로 쓰지 않습니다 — 한글·공백·중복이 섞이고, 파일명 자체가 개인정보인 경우가 있습니다(`홍길동_자격증.jpg`)
- **프로그램 이미지는 `programId`가 있어야 경로가 정해집니다.** 따라서 등록 화면의 순서가 이렇게 됩니다: **① `POST /programs`로 draft 먼저 생성 → ② 사진 업로드 → ③ `PATCH /programs/{id}`로 주소 반영.** 사진을 먼저 고르고 나중에 저장하는 흐름은 만들 수 없습니다(경로가 없으므로). 화면에서는 "기본 정보 저장 → 사진 추가" 2단계로 보이게 합니다

### 18-4. 업로드는 클라이언트가 직접 합니다 — Cloud Functions를 거치지 않습니다

Firestore 쓰기는 전부 서버를 거치게 해뒀는데(1번 원칙), **파일은 예외로 둡니다.** 근거는 셋입니다.

1. **함수로 프록시하면 실제로 막힙니다.** Cloud Functions의 요청 본문 상한과 실행 시간 제한에 사진 여러 장이 걸립니다. 통과하더라도 파일이 함수 메모리를 그대로 통과하므로 비용과 지연이 파일 크기에 비례해 늘어납니다
2. **파일에는 돈·권한·상태가 걸려 있지 않습니다.** 서버 경유를 강제한 이유는 금액·역할·예약 상태를 클라이언트가 정하지 못하게 하려는 것이었습니다(1번). 이미지에는 그런 값이 없습니다
3. **검증해야 할 항목이 규칙으로 전부 표현됩니다** — 경로 소유권, 파일 크기, MIME 타입. 서버 코드로만 할 수 있는 판단이 없습니다

다만 **Firestore에 주소를 반영하는 것은 서버가 합니다.** 클라이언트가 `imageUrls`를 직접 쓰면 남의 파일 주소나 외부 URL을 심을 수 있습니다. 업로드는 클라이언트, 기록은 서버 — 이 분리를 지킵니다.

### 18-5. 보안규칙 전문 (`storage.rules`)

**전문은 리포의 `storage.rules`이고, 교차검증(18-8)과 테스트 16종을 거친 상태입니다.** 여기에는 규칙이 왜 그 모양인지만 적습니다.

| 경로 | read | create/update | delete |
|---|---|---|---|
| `programs/{programId}/{fileId}` | **전체 공개** | 소유 공급자 + 이미지 + 5MB 미만 | **거부** (서버가 정리) |
| `providerCertificates/{uid}/{fileId}` | **전면 거부** (서명 URL로만) | 본인 + 이미지 + 5MB 미만 | **거부** |

**① `write`로 묶지 않고 `create, update`와 `delete`를 나눕니다.** `allow write`는 삭제까지 포함하는데, **삭제 요청에는 `request.resource`가 없어** 크기·타입 검사가 평가 에러로 끝납니다. 그러면 "왜 안 지워지는지" 원인이 규칙인지 데이터인지 드러나지 않습니다. 나눠서 `delete: if false`로 명시합니다 — 파일 정리는 서버가 합니다(18-7).

**② `firestore.get()` 앞에 `firestore.exists()`를 둡니다.** 참조하는 프로그램 문서가 없으면 `get()`은 값을 못 찾는 게 아니라 **평가가 에러로 끝납니다.** 결과는 어느 쪽이든 거부지만, 실패 원인이 구분되지 않습니다. 대신 업로드 1회당 Firestore 읽기가 1~2회 발생합니다 — 업로드는 빈번한 동작이 아니라 감수합니다. **읽기 규칙에는 절대 넣지 않습니다.** 넣으면 사진 한 장 볼 때마다 Firestore 읽기가 발생합니다.

**③ 자격증은 본인에게도 직접 읽기를 열지 않습니다.** 열어두면 클라이언트가 `getDownloadURL()`로 **만료 없는 영구 주소**를 뽑아낼 수 있어, 서명 URL로만 열람한다는 결정(18-6)이 그대로 우회됩니다. 대가로 공급자는 자기가 올린 자격증의 미리보기를 볼 수 없습니다 — 미리보기가 필요하면 그것도 서버가 서명 URL을 발급합니다.

**④ 타입·확장자 검사는 방어선이 아닙니다.** `contentType`도 파일명도 **클라이언트가 정하는 값**이라, 작정하면 `.exe`를 `image/jpeg`·`a.jpg`로 위장해 올릴 수 있습니다. 실수로 올린 엉뚱한 파일을 걸러줄 뿐입니다. 실제 방어선은 **경로 소유권 · 크기 상한 · 저장 도메인이 서비스와 다른 오리진이라는 점**(저장된 파일이 우리 화면의 스크립트로 실행되지 않음)입니다. 검사를 넣되 이걸로 막았다고 여기지 않습니다.

> **주의 — Storage 규칙은 Firestore 규칙과 별개 파일입니다.** 이름과 문법이 비슷해서 한쪽만 고치고 다 됐다고 착각하기 쉽습니다. `firestore.rules`를 고쳐도 파일 접근은 하나도 달라지지 않습니다. `firebase.json`에 `storage.rules` 항목을 넣어야 배포됩니다.
>
> **에뮬레이터는 문법이 깨진 규칙에도 그냥 뜹니다.** "에뮬레이터가 떴으니 규칙이 맞다"는 확인이 되지 않습니다 — 검증은 요청을 보내는 테스트로만 됩니다(18-7).

### 18-6. 자격증을 관리자에게 보여주는 방법 — 다운로드 URL을 쓰지 않습니다

Firebase Storage의 `getDownloadURL()`이 주는 주소에는 **만료가 없는 토큰**이 붙습니다. 그 주소를 한 번이라도 흘리면(브라우저 기록, 캡처, 로그) 토큰을 수동으로 무효화하기 전까지 **누구나 영구히** 자격증을 열 수 있습니다. 로그인도 필요 없습니다.

따라서 자격증은 **서버가 짧은 만료의 서명 URL(signed URL, 5분)을 발급해** 관리자 화면에 내려보냅니다. `GET /admin/providers` 응답의 `certificateImageUrls`를 그때그때 서명 URL로 바꿔서 주는 방식입니다.

- 문서(`private/profile.certificateImageUrls`)에는 **파일 경로만** 저장합니다. 서명 URL을 저장하면 만료된 주소가 남습니다
- 프로그램 이미지는 공개라 이 처리가 필요 없습니다 — 다운로드 URL을 그대로 `imageUrls`에 저장합니다

> ### ⚠️ 서명 URL은 IAM 권한을 따로 줘야 발급됩니다 (오픈 전 필수 작업)
>
> Cloud Functions 2세대의 기본 서비스 계정에는 서명에 쓸 개인키가 없습니다. Admin SDK의 `getSignedUrl()`은 IAM의 `signBlob`을 대신 호출하는데, **기본 권한으로는 거부되어 발급이 실패합니다.** 코드를 아무리 고쳐도 안 됩니다.
>
> GCP 콘솔 → IAM에서 **함수가 쓰는 서비스 계정에 `서비스 계정 토큰 생성자(roles/iam.serviceAccountTokenCreator)`를 부여**해야 합니다. 자격증 열람을 구현하는 날 이것부터 확인합니다 — 모르면 "코드가 틀렸나" 하며 한참 헤매게 됩니다.
>
> 이 설정을 피하려고 파일을 함수가 직접 읽어 내려보내는 방법도 검토했지만 채택하지 않았습니다. 화면은 `<img>` 태그로 이미지를 표시하는데 **`<img>`는 인증 헤더를 실을 수 없어서**, 결국 주소만으로 열리는 무언가를 발급해야 합니다. 그렇다면 만료가 있는 서명 URL이 가장 안전합니다.

### 18-7. 함께 정해둔 것

- **장수 제한**은 화면에서 겁니다 — 프로그램 대표 사진 3~10장(2-3 v9). 규칙으로는 장수를 셀 수 없습니다(파일 하나하나가 개별 요청이라 총 개수를 알 수 없음). 서버의 `PATCH /programs/{id}`에서 `imageUrls` 길이를 검증합니다
- **교체·삭제 시 이전 파일 정리**는 서버가 합니다. `imageUrls`에서 빠진 파일을 지우지 않으면 아무도 참조하지 않는 파일이 계속 쌓입니다. `programs` 문서 자체는 삭제하지 않으므로(6-1 `allow delete: if false`) 문서 삭제로 인한 고아 파일은 생기지 않습니다
- **고아 파일의 진짜 원인은 「올리고 나서 작성을 그만둔」 경우입니다.** draft를 만들고 사진만 올린 뒤 떠나면 아무도 참조하지 않는 파일이 남습니다. **버킷 수명주기(lifecycle) 규칙으로는 이걸 지울 수 없습니다** — 수명주기는 경로와 나이만 볼 뿐 "문서에서 참조 중인지"를 모르므로, 정식 경로에 30일 규칙을 걸면 **멀쩡히 게시 중인 프로그램 사진이 지워집니다.** 대응은 둘 중 하나입니다: ⓐ 서버가 주기적으로 `programs` 전체의 `imageUrls`와 버킷을 대조해 미참조 파일을 지운다 ⓑ `temp/{uid}/…`에 먼저 받고 저장이 확정될 때 정식 경로로 옮긴 뒤, **`temp/`에만** 수명주기 규칙을 건다. ⓑ가 근본적이지만 이동 단계가 늘어나므로, 파일이 쌓이는 속도를 보고 정합니다
- **이미지 리사이즈·썸네일 생성은 P2입니다.** 원본을 그대로 서빙해도 지금 규모에서는 문제가 없고, 필요해지면 Firebase 확장(Resize Images)으로 붙일 수 있습니다. 먼저 하면 안 되는 이유는 없지만, 없어서 막히는 것도 없습니다
- **규칙 테스트 16종**을 6-3과 같은 방식으로 Storage 에뮬레이터에서 돌립니다(`tests/rules/storage.test.ts`, `npm test`에 포함). 핵심은 자격증 읽기 4종 — 비로그인·다른 공급자·**본인**·**관리자** 모두 클라이언트 직접 읽기가 거부되는지. **뒤 둘이 이 설계의 핵심이고 눈으로는 확인할 수 없습니다.** 규칙을 일부러 되돌려 테스트가 그 둘만 정확히 실패시키는 것까지 확인했습니다

### 18-8. 초안 교차검증에서 잡힌 결함 (v16 안에서 수정 완료)

18번 초안을 작성한 직후 외부 모델로 교차검증했습니다. **실제로 고쳐야 할 지적 4건과, 사실과 다른 지적 2건이 나왔습니다.** 판단 근거를 남깁니다 — 나중에 같은 논의가 다시 나올 때 되짚기 위함입니다.

**반영한 것**

| 등급 | 지적 | 처리 |
|---|---|---|
| 치명 | `allow write`가 삭제까지 포함하는데 삭제 요청에는 `request.resource`가 없어 타입·크기 검사가 평가 에러로 끝남 | `create, update`와 `delete`를 분리. 삭제는 `if false`(서버 전용, 18-5 ①) |
| 치명 | 서명 URL은 Cloud Functions 기본 서비스 계정으로 **발급되지 않음** — IAM `signBlob` 권한이 없음 | 18-6에 오픈 전 필수 작업으로 명시. 코드로는 해결 불가라 모르면 원인을 못 찾습니다 |
| 보통 | 자격증 read를 본인에게 열어두면 `getDownloadURL()`로 만료 없는 주소를 뽑아 서명 URL 결정이 우회됨 | `allow read: if false`로 전면 차단(18-5 ③) |
| 보통 | `firestore.get()`은 문서가 없을 때 평가 에러로 끝남 | `firestore.exists()` 가드 선행(18-5 ②) |

**반영하되 효과를 과대평가하지 않은 것**

- **확장자 검증 추가** — 파일명도 클라이언트가 정하는 값이라 `.jpg`로 이름만 바꾸면 그만입니다. 위장을 막지 못합니다. 넣되 방어선으로 세지 않습니다(18-5 ④).

**반영하지 않은 것**

- **"관리자가 파일을 삭제할 수 있게 `isAdmin()`을 넣어야 한다"** — 사실과 다릅니다. **Firebase 콘솔과 Admin SDK는 보안규칙을 우회하므로** 관리자는 이 규칙과 무관하게 이미 삭제할 수 있습니다. 관리자 화면도 클라이언트 SDK가 아니라 `/admin/*` 서버 API를 쓰므로(12-2), 규칙에 `isAdmin()`을 넣으면 **쓰이지도 않는 권한을 여는 것**이 됩니다.
- **"버킷 수명주기 규칙으로 30일 지난 미연결 파일을 자동 삭제"** — 수명주기 규칙은 경로와 나이만 볼 뿐 **문서에서 참조 중인지 알지 못합니다.** 정식 경로에 걸면 게시 중인 프로그램 사진이 지워집니다. `temp/` 경로를 따로 둘 때만 성립하는 방법이라 18-7에 조건과 함께 적었습니다.

> **교차검증 자체에서 얻은 교훈이 하나 더 있습니다.** 규칙 파일이 문법상 유효한지 확인하려고 에뮬레이터를 띄워봤는데, **문법을 일부러 깨뜨려도 에뮬레이터는 그냥 떴습니다.** "에뮬레이터가 정상 기동했다"는 규칙 검증이 아닙니다. 검증은 요청을 보내는 테스트로만 됩니다 — 그래서 테스트를 먼저 쓰고, 규칙을 되돌려 테스트가 실제로 실패하는지까지 확인했습니다.

## 검토 결과 판단 근거

**v1→v2 반영(진짜 결함/법적 요구):** 스케줄 정원 공유 버그, 오버부킹/TTL홀드, 웹훅 멱등성, 원천징수 계산기준, `minCapacity`, `termsAgreements`, `settlementItems`, 보안규칙 구체화(role/price 권한상승 방지) — 모두 코드가 실제로 틀리게 동작하거나 법적 리스크가 있는 부분이라 반영.

**v1→v2 팀 확인 후 결정(엔지니어링이 아니라 기획 문제):** `open` 스케줄 정의, 환불 2~6일 구간 해석 — 임의로 결정하지 않음.

**v1→v2 보류(스코프 크리프/UI 미확정):** 바우처 성과추적, 인앱 알림센터, 환불계좌 필드, 리뷰 사진/답글.

**v2→v3 반영:** `schedules`/`scheduleTemplates` 보안규칙 추가(정원 조작 방지), 템플릿 수정 캐스케이딩 정책 + 전용 API 추가. 이 과정에서 "템플릿 클라이언트 직접 쓰기 허용"과 "캐스케이딩 정책 강제"가 서로 충돌한다는 걸 발견해, `scheduleTemplates`를 서버 전용 쓰기로 통일함.

**v2→v3 반영 안 함:** "open 대안 스키마 준비"는 이미 v2의 2-4 하단에 동일 내용(A안/B안 분기)이 있어 중복 — 추가 변경 없음.

**v3→v4 반영 (2026-08-07 팀 회의 확정):** `open` 스케줄을 협의형 예약(정원 없음)으로 확정하고 `schedules` 서브컬렉션 대신 `bookings.negotiatedDate`/`checkInAt`으로 설계. 환불 2~6일 구간을 50%로, 기준일을 진행일로 최종 확정(벤치마킹 리서치로 다수 관행과 일치 확인). 공급자 귀책 취소에 대한 페널티를 신규 설계했는데, 팀 논의 결과 정산금 차감(수수료) 방식은 채택하지 않고 **경고 누적 → 활동 제한(비금전적 제재)**으로 결정 — `providerProfiles.warningCount`/`activityRestriction` 필드와 `violations` 서브컬렉션 추가. 환불·페널티 면제 사유를 천재지변/본인 질병·사고/직계가족 상 3가지로 통일(`exemptReason`). 벤치마킹 리포트에 있던 "최소인원 미달 D-1 자동취소 + 공급자 수동 강제개설" 로직을 `checkMinCapacity` 스케줄 함수와 `schedules.forceOpen` 필드로 구체화. 웹 환경(푸시 알림 불가)의 한계를 보완하기 위해 1:1 문의 답변 도착 시 알림톡/SMS 발송 트리거를 추가.

**v4→v5 반영 (2026-08-07, 팀 회의 종료 후 구현 관점 자체 재검토 — 새 의사결정 아님, 실행 공백 보완):** ① `bookings.status`가 `confirmed→completed`로 전환될 트리거가 문서 전체에 없었음(리뷰 조건·정산 대상 판단이 이 값에 의존하는데 아무도 이 값을 세팅 안 하는 구조였음) → `markBookingsCompleted` 스케줄 함수 추가. ② `open` 타입은 `negotiatedDate` 확정 전 취소 시 적용할 "진행일"이 없어 환불 로직에 빈틈이 있었음 → 협의 전=전액환불로 명시. ③ 10번(구 9번)에 실체 없이 남아있던 `checkPenalty` 스케줄 함수 언급 삭제(페널티는 취소 API 안에서 즉시 처리). ④ `programs` 보안규칙이 소유자의 `status` 직접 수정을 막는데 draft→pending_review 전환 API가 없었음 → `POST /programs/{id}/submit-for-review` 추가.

**v9→v10 반영 (2026-08-11, 보안 전면 점검):** v9의 관리자 페이지 설계를 제미나이로 교차검증하는 과정에서, 기존 보안규칙이 **배포조차 되지 않는 상태**임이 확인됐습니다. 정의되지 않은 함수 3개를 호출하고 있었고, 컬렉션 7종에는 규칙 자체가 없어 기본 거부에 걸렸습니다(보안 구멍이 아니라 조회 불가). 더 심각한 것은 `users`의 `create` 규칙에 필드 검증이 없어 **회원가입만으로 관리자 권한을 자가 부여할 수 있었다**는 점입니다 — `update`는 막아뒀는데 `create`가 열려 있어 우회가 가능했습니다. 결제 웹훅에 금액 대조가 없어 프론트 조작으로 결제액을 낮출 수 있었던 것, 리뷰 생성 규칙이 예약 소유권을 확인하지 않아 남의 예약 ID로 거짓 리뷰를 쓸 수 있었던 것도 같은 검증에서 나왔습니다. `providerProfiles`는 규칙 수정만으로 해결되지 않아(Firestore는 필드 단위 읽기 제어 불가) 문서 구조를 공개/비공개로 분리했습니다. **모두 새 기능이 아니라 이미 정한 설계를 실제로 안전하게 동작시키기 위한 수정**이며, 13번에 처리 우선순위를 정리했습니다.

**v10→v11 반영 (2026-08-13):** 로그인 방식을 "소셜 3종 나열"에서 "가입은 소셜 2종, 본인확인은 결제·공급자 등록 시점"으로 바꿨습니다. 국내 플랫폼 관행 확인 결과 가입 문턱을 낮추고 인증을 뒤로 미루는 것이 표준이었고, 우리 문서의 "문자인증"이라는 표현이 SMS OTP와 휴대폰 본인확인을 구분하지 않아 구현 시 잘못된 선택을 할 위험이 있었습니다. 날씨는 상세·회차별로 확대하면서 캐싱 전략(격자 단위 3시간)과 예보 기간 한계 처리를 미리 정해, 화면이 늘어도 비용이 늘지 않는 구조로 못박았습니다.

**v11→v12 반영 (2026-08-13, 팀 회의):** 소비자 본인확인을 철회했습니다. 회의에서 "유아숲체험은 부모가 결제한다"는 지적이 나오면서, 결제자 본인확인으로 참가 아동의 나이를 알 수 없다는 점이 드러났습니다. 검토 결과 미성년자 판별·사고 대응·어뷰징 방어 세 가지 근거가 모두 다른 수단으로 대체되거나 애초에 성립하지 않았습니다 — 앞의 둘은 예약 폼(15-6)이, 어뷰징은 전화번호 중복 체크가 담당합니다. 결제 수단 검증은 PG가 이미 처리하고, 사용자가 결제 시 겪는 "인증"의 대부분은 본인확인이 아니라 카드사 인증이라는 점도 확인했습니다. **소비자 쪽에서 기능을 뺀 대신 예약 폼을 강화**했고, `bookings`에 참가자·보호자·비상연락처 필드를 신설했습니다. 대상연령 필드는 이 폼의 선행 조건이라 P2에서 P1으로 올렸습니다. 부수 효과로 본인확인 사용량이 공급자 등록 시점만 남아 연간 비용이 1만원 미만으로 줄었습니다.

**v12→v13 반영 (2026-08-13, 검색 필터 기획):** 필터를 **화면부터 프로토타입으로 만들어 확정한 뒤 필요한 필드를 역산**했습니다. 그 결과 **정렬 6종 중 3종(인기순·신규순·평점순)이 기준 필드 없이 화면에만 존재**했다는 사실이 드러났습니다 — 스키마만 들여다봐서는 발견하기 어려운 종류의 공백입니다. 기술적으로 가장 중요한 결정은 **필터를 클라이언트 Firestore 쿼리로 만들지 않기로 한 것**입니다. Firestore는 쿼리 하나를 논리합 30개로 제한하는데, 카테고리 다중선택(5)과 대상연령 다중선택(6)만으로 이미 30에 닿고 기간까지 얹으면 930으로 넘칩니다. 필터 조합마다 복합 인덱스가 필요하다는 문제도 겹쳐, 검색을 Cloud Function 하나로 모으고 메모리 캐시를 두는 구조로 정했습니다(17-1). 기간 필터는 날짜가 하위 `schedules`에 있어 조인 없는 Firestore에서는 한 번에 조회할 수 없었고, 세 가지 방법을 비교해 `programs.scheduleDates` 비정규화를 택했습니다(17-2) — 대신 갱신 지점이 흩어지면 달력과 실제 예약이 어긋나므로 단일 함수로 묶었습니다. 부수적으로 **캘린더 이동 범위(5개월)와 회차 생성 롤링 윈도우(8주)가 어긋나 있던 문제**를 발견해 둘 다 90일로 통일했고, 13번 P2에 "숲 특화 필터"로 뭉뚱그려 보류돼 있던 난이도·보행거리와 평점 캐시가 실제로는 정렬에 필수인 필드였음을 확인해 P1으로 올렸습니다.

**v13 자체 교차검증 (같은 날, 팀 전달 전):** 17번을 쓴 직후 별도 검토를 돌려 결함 8건을 잡아 같은 버전 안에서 고쳤습니다(17-7). 가장 무거운 것은 **파생 필드를 추가하면서 보안규칙을 함께 보지 않은 것**입니다 — 기존 규칙이 금지목록 방식이라 새 필드가 전부 열려 있었고, 공급자가 브라우저 콘솔로 평점과 예약 수를 조작해 검색 1위를 차지할 수 있었습니다. v10에서 `users` create에 필드 검증이 없어 권한 상승이 가능했던 것과 **같은 종류의 실수**입니다(금지목록은 빠뜨리면 사고, 허용목록은 빠뜨리면 버그). 두 번째는 **Firestore가 인덱스 필드에 값이 없는 문서를 색인하지 않는다**는 성질을 놓쳐 상시모집 프로그램이 검색에서 사라질 설계였던 것이고, 세 번째는 캐시 비용을 시간당 수치를 일 단위로 적어 **24배 과소 추정**한 산수 오류였습니다. 이 세 번째는 검증 없이 넘어갔다면 정식 오픈 후 요금 청구로 발견됐을 항목입니다.
