## 1. 즉시 조치 (지금 고치는 것이 맞는 것)

### 1-1. v18 이전 프로그램을 수정하면 좌표가 (0, 0)으로 저장됨

- **무엇이 문제인가** — 좌표가 비어 있던(null) 프로그램을 수정 화면에서 한 번이라도 저장하면, 좌표가 「없음」이 아니라 「위도 0 · 경도 0」(기니만 앞바다)으로 바뀝니다.
- **어디인가** — `src/pages/ProgramRegisterPage.tsx:207-208` (`lat: res.program.location.lat ?? 0`), 서버 쪽 수용 지점은 `functions/src/lib/programs.ts:161-162`
- **어떻게 드러나는가** — ① v18 이전에 등록돼 좌표가 null인 프로그램을 소유자가 「수정」으로 엶 ② 주소를 다시 검색하지 않고 제목만 고쳐 저장 ③ 화면이 `place.lat = null ?? 0`으로 만든 0을 그대로 보내고 서버가 저장 ④ 상세 화면의 `hasCoords`(`lat != null`) 검사가 이제 참이 되어, **지도가 아프리카 앞바다를 중심으로 그려지고** 날씨는 「예보를 제공하지 않는 지역입니다」가 됩니다.
- **왜 문제인가** — 「좌표 없음(안내 문구로 대체)」이라는 정상 폴백이 「틀린 좌표(지도에 엉뚱한 곳)」로 바뀝니다. 에러가 없어 공급자도 관리자도 알아차릴 수 없고, CLAUDE.md의 「v18 이전 프로그램은 백필 필요」 전제가 「수정하면 더 나빠짐」으로 악화됩니다.
- **고치는 방향** — 화면에서 좌표가 null이면 null 그대로 보내기(0으로 치환하지 않기). 서버도 위도·경도의 **상한**(90/180)을 검증해 방어선을 하나 더 두면 좋습니다(지금은 하한만 검사).
- **확실도** — **코드로 확인** (화면 → 서버 → 상세 표시까지 경로 전부 코드로 추적. 실행 재현은 안 함)

### 2-4. 사진 주소 검증이 부분일치라, 같은 버킷의 다른 파일 주소를 심을 수 있음

- **무엇이 문제인가** — 사진 등록 시 「주소가 그 파일을 가리키는가」 검사가 `url.includes(인코딩된 경로)` **부분 문자열 포함**이라, 실제로는 다른 객체를 가리키면서 검사만 통과하는 주소를 만들 수 있습니다.
- **어디인가** — `functions/src/lib/programImages.ts:82-96` (`assertUrlPointsToPath`)
- **어떻게 드러나는가** — 소유자가 자기 경로의 파일을 정상 업로드한 뒤, `https://firebasestorage.googleapis.com/v0/b/{버킷}/o/{남의 게시 프로그램 사진 경로}?alt=media&x={자기 경로 인코딩}` 처럼 **자기 경로를 쿼리스트링에 끼워 넣은** 주소로 `POST /images`를 호출하면 — 호스트 검사와 포함 검사를 모두 통과해, `imagePaths`는 자기 파일을 가리키는데 `imageUrls`(화면에 보이는 사진)는 남의 사진이 됩니다. 이 값이 검색 카드·상세 슬라이더에 그대로 쓰입니다.
- **왜 문제인가** — 외부 URL은 호스트 검사로 막히지만 **같은 버킷 안의 공개 파일**(다른 프로그램의 사진)은 막지 못합니다. 남의 사진 도용, 삭제 시 경로·주소 불일치(자기 파일은 지워지는데 화면 사진은 남음)로 이어집니다. 자격증 등 비공개 파일은 규칙상 열리지 않아 노출까지는 안 갑니다.
- **고치는 방향** — 주소를 파싱해 **객체 경로가 정확히 일치**하는지 비교(포함이 아니라 동등 비교). 또는 아예 클라이언트 주소를 버리고 경로에서 서버가 다운로드 주소를 만들어 저장.
- **확실도** — **코드로 확인** (검사 로직은 확정. 배포 환경의 실제 URL 형식으로 우회 문자열이 성립하는지는 실행으로는 미확인 — 「의심되지만 미확인」에 가까운 절반)

### 2-5. 이용 정지·자격 회수된 공급자가 기존 프로그램을 계속 운영할 수 있음

### 3-1. 수정 화면에서 사진을 만지면 저장 안 한 편집 내용이 서버 값으로 되돌아감

- **어디인가** — `src/pages/ProgramRegisterPage.tsx:827` (`onChanged={loadProgram}`) + `loadProgram`(189-222)이 `includes`/`excludes`/`preparations`/`introBlocks`/`capacity`/`scheduleType` 상태를 서버 값으로 재설정
- **어떻게 드러나는가** — ① 수정 화면에서 포함 키워드를 바꿈(아직 저장 전) ② 「프로그램 사진」에서 사진을 한 장 추가하거나 지움(즉시 서버 반영 → 화면이 프로그램을 다시 불러옴) ③ **방금 바꾼 키워드 선택이 소리 없이 원래대로 돌아갑니다.** 제목 등 일반 입력칸은 남고, 칩·블록 등 상태로 관리하는 값만 되돌아가서 더 알아차리기 어렵습니다. 그대로 저장하면 편집이 유실됩니다.
- **고치는 방향** — 사진 변경 후 재조회 시 사진 관련 상태만 갱신하고 편집 중인 콘텐츠 상태는 보존.
- **확실도** — 코드로 확인 (React 상태 흐름 기준. 실행 재현은 안 함)

### 3-2. 사진 등록·삭제·순서 변경이 트랜잭션 없이 읽고-쓰기

- **어디인가** — `functions/src/lib/programImages.ts` 세 함수 모두 (읽기 → 배열 계산 → update)
- **어떻게 드러나는가** — 같은 프로그램에 두 요청이 겹치면(예: 삭제와 순서 변경을 연타) 나중 쓰기가 앞의 결과를 덮습니다 — 지운 사진의 주소가 되살아나 깨진 이미지가 남거나, 동시 추가 두 건이 각각 검사를 통과해 5장 상한을 넘을 수 있습니다.
- **왜 문제인가** — 한 명이 조작하는 화면이라 확률은 낮지만, 「문서를 먼저 고치고 파일을 지운다」는 원칙이 경합에서는 깨집니다.
- **고치는 방향** — 세 함수의 읽기-쓰기를 Firestore 트랜잭션으로 감싸기.
- **확실도** — 코드로 확인 (경합 자체는 이론적 — 재현 안 함)

### 3-3. 수정 저장과 관리자 승인이 겹치면 미심사 내용이 게시본에 들어갈 수 있음

- **어디인가** — `functions/src/lib/programs.ts:572` 이하 (`updateProgram` — 상태를 읽은 뒤 트랜잭션 없이 update)
- **어떻게 드러나는가** — 프로그램이 `pending_review`일 때 소유자가 PATCH를 보내고, 그 **읽기와 쓰기 사이에** 관리자 승인이 끼어들면 — 화면상 이미 게시된 프로그램에 심사를 안 거친 내용이 그대로 덮입니다(승인 트랜잭션이 재계산한 파생 필드도 함께 덮일 수 있음).
- **고치는 방향** — `updateProgram`도 트랜잭션으로 상태를 다시 읽고 분기. `submitProgramForReview`는 이미 트랜잭션이라 같은 모양으로 맞추면 됩니다.
- **확실도** — 코드로 확인 (창이 밀리초 단위라 실발생 확률은 낮음 — 경합 재현 안 함)

### 3-4. 날씨 API — 비로그인 + 임의 좌표라 격자 사전 조회로 기상청 쿼터를 태울 수 있음

- **어디인가** — `functions/src/http/routes/external.ts` (`GET /external/weather`, 인증 없음) / 한반도 범위 제한: `kmaGrid.ts:isInKorea`
- **어떻게 드러나는가** — 누구나 좌표를 바꿔가며 호출하면 격자(5km)마다 발표본당 기상청 1회 + `weatherCache` 문서 1개가 생깁니다. 한반도 범위(위도 32~40, 경도 124~132)로 제한돼 있어 무한하지는 않지만, 격자 수가 수만 단위라 3시간마다 수만 호출·수만 문서까지는 열려 있습니다. TTL 미설정 상태라 문서는 계속 쌓입니다.
- **왜 문제인가** — 정상 사용에서는 캐시 설계가 잘 동작하지만(방문자 수가 아니라 격자 수에 비례 — 확인함), 악의적 사전 조회에는 상한이 없습니다. 공공데이터포털 무료 쿼터가 막히면 정상 방문자의 날씨도 함께 죽습니다.
- **고치는 방향** — 좌표를 임의 수신하지 말고 **프로그램 id로 받아 서버가 저장된 좌표를 쓰는** 방식이 근본적입니다(상세 화면 전용이 된 v29 구조와도 맞음). 최소한으로는 호출량 상한.
- **확실도** — 코드로 확인 (쿼터 한도 수치는 미확인 — 「의심되지만 미확인」)

### 3-5. Storage 직접 업로드는 문서에 기록하지 않아도 쌓임 — 정리 수단 없음

- **어디인가** — `storage.rules`의 `programs/{programId}/{fileId}` create 허용(소유자·5MB·이미지 타입만 검사) + 미참조 파일 정리 부재(18-7, 알려진 공백)
- **어떻게 드러나는가** — 소유자가 `POST /images`를 부르지 않고 Storage SDK로만 반복 업로드하면 장수 제한(5장)과 무관하게 파일이 무한정 쌓입니다. 규칙으로는 개수를 못 세는 것이 문서에 적힌 그대로이고, 지우는 배치가 없어 비용으로만 드러납니다. 등록 화면의 정상 흐름에서도 「업로드 성공 → 기록 실패」가 나면 같은 미참조 파일이 남습니다(`ProgramRegisterPage.tsx:553-590`의 실패 처리 참고 — 프로그램은 살리고 파일은 남김, 의도된 트레이드오프).
- **고치는 방향** — 18-7에 이미 계획된 미참조 파일 정리 배치를 예약 기능 전에 한 번 만들기. 업로드 남용은 정리 배치가 있으면 비용 문제로 축소됩니다.
- **확실도** — 코드로 확인 (남용 시나리오 자체는 실행 안 함)

### 3-6. 위도·경도 상한, `availableFrom`/`availableUntil` 타입 미검증

- **어디인가** — `functions/src/lib/programs.ts:161-162` (min만 검사, max 없음) · 169-170 (`b.availableFrom as string` — 형식·타입 검증 없이 저장)
- **어떻게 드러나는가** — API를 직접 부르면 위도 999나 `availableFrom: {"x":1}` 같은 값이 프로그램 문서에 그대로 저장됩니다. 화면은 주소 검색으로만 좌표를 만들어 정상 흐름에서는 안 생기지만, 저장된 뒤에는 지도·날씨·상시모집 표시가 조용히 이상해집니다.
- **고치는 방향** — 위도 ≤90 / 경도 ≤180 상한, `availableFrom/Until`은 날짜 문자열 형식 검사(`kstToInstant`의 정규식 재사용 가능).
- **확실도** — 코드로 확인

### 3-7. 등록 중 사진 흐름의 안내 문구가 실제 실패 지점과 어긋날 수 있음

- **어디인가** — `src/pages/ProgramRegisterPage.tsx:553-590` (사진 업로드~소개 블록 연결이 한 try에 묶임)
- **어떻게 드러나는가** — 사진 업로드와 기록(`POST /images`)까지 성공하고 **소개 블록 연결 PATCH만** 실패한 경우에도 「사진을 올리지 못했습니다」가 떠서, 사용자가 이미 올라간 사진을 다시 올리게 됩니다(중복 등록은 서버가 거부하니 데이터는 안 깨지지만 혼란).
- **고치는 방향** — 연결 단계 실패를 따로 잡아 「사진은 올라갔고 소개 글 연결만 남았습니다」로 안내.
- **확실도** — 코드로 확인

### 3-8. `pending:` 임시 경로 — 서버 유입 없음 확인, 다만 방어는 간접적

- 점검 요청 항목이라 결과를 적습니다. 등록 시 소개 블록 사진은 `images: []`로 비워 보내고(`ProgramRegisterPage.tsx:540`), 연결 단계는 업로드로 얻은 실제 경로만 넣습니다(flatMap으로 미해결 경로 탈락). 혹시 새어 들어가도 서버의 「사진 목록에 없는 경로 거부」(`programs.ts resolveIntroBlockImages`)가 막습니다 — **구멍 없음, 코드로 확인.** `pending:` 접두사를 서버가 명시적으로 아는 것은 아니므로(목록 대조에 의존) 주석 정도만 남겨두면 충분합니다.

## 6. 문제 없음을 확인한 것 (다음 점검에서 건너뛰어도 되는 곳)

**권한·인증**
- `/admin/*` 차단선 — 라우터 첫 줄 `router.use(authenticate, requireAdmin)` 하나로 전 경로 적용(`routes/admin.ts:41`), `assertAdmin`은 `admin === true` 엄격 비교(`authz.ts`). 검사 빠진 관리자 경로 **없음**
- `firestore.rules` — `users` 생성 시 role/status 기본값 강제, 수정 시 role/status 변경 차단, `programs` 수정 허용목록(파생 필드 전부 차단), `pendingEdit`/`scheduleTemplates`/`private` 하위 소유자·관리자 한정, `phoneIndex` 전면 차단, 명시 없는 경로 기본 거부 — 전부 문서(6-1)와 일치
- `storage.rules` — 자격증 본인 읽기까지 차단(서명 URL 설계 유지), 프로그램 사진은 소유자만 쓰기, create/update와 delete 분리 — 문서(18-5)와 일치
- 소셜 uid — 카카오 회원번호는 안전 정수만 문자열화, 없으면 실패(`kakao_undefined` 계열 사고 차단, `kakao.ts:56-66`). 네이버도 id 없으면 실패. 재로그인 시 role·name 절대 미덮어쓰기(`socialAuth.ts`). state 대조는 프론트 콜백에서 수행, 카카오 redirectUri는 서버 허용목록 대조
- `users.role` 클라이언트 쓰기 경로 — 규칙·서버 모두 없음. grant 스크립트는 HTTP 미노출(스크립트 전용)

**민감 정보**

- **어디인가** — `firestore.rules:95-102`의 draft 수정 허용목록에 `'imageUrls'`가 들어 있음(101행). `MD/backend/백엔드-설계-스키마.md` 6-1(692행 부근)도 같은 내용.
- **어떻게 드러나는가** — 공급자가 자기 draft 문서에 Firestore SDK로 `imageUrls: ["https://아무서버/x.jpg"]`를 직접 써도 규칙이 통과합니다. 서버 경로(`POST /programs/{id}/images`)의 네 가지 검사(소유 폴더·버킷 존재·호스트·주소↔경로 일치)를 전부 건너뛰고, `imagePaths`·`thumbUrls`·`thumbPaths`는 허용목록에 없어 그대로라 **네 목록의 길이가 어긋납니다.** 그 뒤 ① 서버의 `padTo`(`programImages.ts:138`)는 썸네일만 맞추고 `imagePaths`는 안 맞춰 순서 변경·삭제가 엉뚱한 자리를 가리킬 수 있고 ② 심사 화면(`AdminPage.tsx:161-166`)이 그 외부 주소를 `<img src>`·`<a target=_blank>`로 그대로 그려 심사자에게 외부 추적 픽셀·피싱 링크가 보일 수 있고(리퍼러는 `noreferrer`로 차단, `javascript:`는 새 창 격리로 무력) ③ 승인되면 목록 카드가 `cardImageUrl()` 되돌림(`cardImage.ts:35`)으로 그 외부 주소를 씁니다. 심사 요청·승인(`adminReview.ts`) 어디에도 `imageUrls` 재검증이 없습니다.
- **심각도 — Medium · 시점 「오픈 전 필수」.** 실행 주체가 공급자 본인(자기 프로그램)이라 남의 데이터에는 닿지 않지만, 「사진은 서버 경로로만 바뀐다」는 절대 규칙(`backend.md`)과 어긋나는 실제 우회 경로입니다.
- **고치는 방향** — **문서(6-1)가 규칙과 같은 내용이라 문서 결정이 먼저입니다 — 임의로 고치지 않았습니다.** 결정되면: 6-1 허용목록에서 `imageUrls`를 빼고(`thumbUrls`처럼) 규칙 테스트에 「draft라도 `imageUrls` 직접 수정 거부」 케이스 추가. 보수적으로는 심사 승인 시 `imageUrls.length === imagePaths.length`와 호스트 재검증 한 줄 더.
- **확실도** — 0.85 (규칙 원문·문서 원문·서버 코드로 확인, SDK 호출 재현은 안 함. 두 검토자 교차 확인)

### B-2. 작은 사진(`thumbPath`)의 중복·겹침을 확인하지 않아 지우기 연쇄로 남은 사진이 깨질 수 있음

- **어디인가** — `functions/src/lib/programImages.ts:220-236`(큰 사진은 `imagePaths.includes`로 중복을 막지만 `thumbPath`는 안 봄), `:295-330`(삭제 시 `removedThumbPath` 파일 삭제).
- **어떻게 드러나는가** — 소유자가 `thumbPath`에 이미 등록된 다른 사진의 경로(또는 두 항목에 같은 경로)를 보내면 통과합니다. 뒤에 한 장을 지우면 그 파일이 지워져 **다른 사진의 작은 판(또는 큰 사진 자체)이 깨진 이미지**가 됩니다.
- **심각도 — Low · 개선.** 자기 프로그램 폴더 안에서만 가능해 남에게 피해는 없고 정합성 문제입니다. 다만 「어긋나도 에러가 안 나고 엉뚱한 사진으로만 드러난다」는 이 기능의 위험 유형 그대로입니다.
- **고치는 방향** — `thumbPath`가 `imagePaths`·기존 `thumbPaths`·같은 요청의 다른 경로와 겹치면 거부(3줄) + 테스트 1건.
- **확실도** — 0.75

### B-3. 화면 껍데기(`index.html`)가 `/`와 모든 화면 주소에서 1시간 캐시로 내려감 — 배포 직후 빈 화면 가능

- **성격** — 가용성/운영(보안 아님). 오늘 실서버 헤더에서 발견.
- **어디인가** — `firebase.json` headers: `no-cache`가 `"source": "/index.html"`에만 걸려 있어 **`/index.html`로 직접 열 때만** 적용됨. 실제 방문 주소인 `/`, `/search`, `/programs/{id}`(SPA rewrite)는 파이어베이스 기본값 **`max-age=3600`**으로 내려감(오늘 `curl -I`로 확인).
- **왜 문제인가** — 새 배포는 `assets/index-{해시}.js` 파일명을 바꾸고 옛 파일을 지웁니다. 1시간 안에 다시 온 방문자는 캐시된 옛 껍데기가 **사라진 파일을 가리켜 빈 화면**을 볼 수 있습니다. 오픈 때 관문 비밀번호를 비우는 배포도 최대 1시간 늦게 반영됩니다. 사진 1년 캐시(9/3)와는 별개입니다(그쪽은 파일명이 난수라 안전).
- **심각도 — Low · 개선(다음 배포 전 권장).** 고치는 방향: `"source": "**"` 블록에 `Cache-Control: no-cache`를 추가(뒤에 오는 `/assets/**` immutable 규칙이 자산에는 그대로 적용됨). 배포 후 `curl -I https://foom.kr/`로 확인.
- **확실도** — 0.9 (실서버 응답으로 확인)

## C. 의존성·비밀값

- **의존성 취약점(`npm audit`)** — 지난주 「중간만」에서 **변동 있음.**

## D. 문제없음을 확인한 것 (이번 범위)

- **썸네일 서버 검증 동등성** — `thumbPath`·`thumbUrl`에 큰 사진과 같은 4단계 검사(`programImages.ts:226-236`), 경로만·주소만 오면 거부(`:87-92`). 테스트 11종이 남의 폴더·외부 서버·버킷 미존재·짝 밀림·옛 문서 순서 변경을 덮음.
- **4목록 불변식(서버 경로 안)** — 추가·삭제·순서 변경 세 경로가 네 목록을 같은 자리로 갱신, 옛 문서는 `padTo`, 초기값 빈 배열(`programs.ts:324-325`). 밖에서 깨지는 경우만 B-1.
- **경로 탐색** — `assertPathBelongsToProgram`이 접두어·`..`·하위 폴더를 막고, 썸네일도 같은 폴더의 `t_{fileId}` 한 단계라 `storage.rules:49-60`과 일치.
- **`thumbUrls`는 어디서도 본문으로 받지 않음** — `ProgramDraftInput`에 없고 보안규칙 허용목록에도 없음. 검색 응답은 첫 장만(`programSearch.ts:391`).
- **사진 1년 캐시 대상** — `storage.rules:51`에서 이미 전체 공개 읽기인 프로그램 사진뿐. 자격증 경로 미접촉. 파일명 난수라 재사용 없음. (지운 사진이 주소를 이미 가진 사람의 캐시에 최대 1년 남을 수 있음 — 수용 가능)
- **DOM XSS** — `innerHTML`·`dangerouslySetInnerHTML`·`window.open` 신규 사용 없음. Lightbox·Gallery·MapCard·ProgramCard는 서버 검증 주소를 `<img src>`에만.
- **길찾기 링크** — 고정 호스트(`map.kakao.com`) + 숫자 좌표 + `encodeURIComponent` 제목, `rel="noreferrer noopener"`. 사용자 좌표 전송은 「내 위치」 → 「길찾기」를 본인이 눌러야만 발생.
- **카카오 콜백 허용목록** — `auth.ts`가 `includes`로 **완전 일치**만 허용(열린 리다이렉트 아님). 오늘 개인 프로젝트 주소 2줄 → 회사 임시 주소 1줄로 정리.
- **`imageResize.ts`** — 파일 타입 화이트리스트 후 canvas 재인코딩이라 원본 형식(HEIC 등)이 그대로 올라가지 않음.
- **SiteGate** — 저장소 접근 try/catch, 실패해도 화면 유지.
- **실서버 로그인** — 회사 프로젝트에서 카카오·네이버 **둘 다 실계정 로그인 성공**(계정 2개 생성 확인) → 토큰 서명 권한(함정 ①) 정상.
