## 절대 규칙

**돈·권한·상태가 걸린 데이터는 클라이언트가 직접 쓰지 않습니다.**
`bookings` `payments` `settlements` `reviews` `providerProfiles` — 전부 Cloud Functions(Admin SDK) 경유. 보안규칙에서 `allow write: if false`로 막혀 있습니다.

**관리자에게도 클라이언트 쓰기를 열지 않습니다.** (`voucherAds`만 예외)
심사·정산은 반드시 `/admin/*` API를 거칩니다. 감사로그를 남겨야 하기 때문입니다.

**보안규칙은 클라이언트 SDK에만 적용됩니다.** Cloud Functions는 Admin SDK라 규칙을 우회합니다. `/admin/*` 함수는 진입부에서 `context.auth.token.admin`을 직접 검사해야 합니다. 프론트 라우트 가드는 UX 장치일 뿐 보안이 아닙니다.

**결제 금액은 서버가 정합니다.** 클라이언트가 보낸 금액은 무시하고 `bookings.totalAmount`를 씁니다. 웹훅에서 실결제액과 대조하되 **기준은 `bookings.unitPrice`(예약 시점 스냅샷)이지 `programs.price`(현재가)가 아닙니다.**

**`users.role`은 어떤 경로로도 클라이언트가 못 씁니다.** 관리자 지정은 Admin SDK 스크립트로 `users.role`과 Custom Claims(`admin: true`)를 **동시에** 갱신합니다. 하나만 하면 화면이 안 열립니다.

**⚠️ Custom Claims에는 성격이 다른 두 종류가 있습니다 — 섞지 마세요** (2026-09-11).

| 클레임 | 쓰임 | 권한 판단에 쓰나 |
|---|---|---|
| `admin` | 보안규칙·함수 진입부(`requireAdmin`)가 보는 값 | **예** — 이것이 기준입니다 |
| `provider` · `providerApproved` | **헤더 버튼을 무엇으로 그릴지만** 정합니다 | **아니오** |

**`provider`·`providerApproved`로 권한을 판단하면 안 됩니다.** 클레임은 이미 발급된 토큰에 소급되지 않아 **최대 1시간 낡을 수 있습니다** — 자격이 회수된 사람이 그 시간 동안 통과하게 됩니다. 전문가 권한 검사는 지금처럼 서버가 `users.role`과 `approvalStatus`를 **직접 읽어서** 합니다(`assertProvider`·`isProviderApproved`). 이 둘을 `requireAdmin` 같은 진입부 검사나 보안규칙에 넣지 마세요.

**대신 로그인할 때마다 회원 정보와 맞춥니다**(`syncProviderClaimsFromDb`, 소셜 로그인 경로). 「로그아웃 후 재로그인」이 언제나 즉시 고치는 방법이 되고, 어긋난 채로 굳지 않습니다. **여기서 실패해도 로그인을 막지 않습니다** — 버튼 모양만 정하는 값이라, 넘어져서 로그인 자체가 실패하면 잃는 것이 훨씬 큽니다.

**가입은 소셜 2종(카카오·네이버)뿐입니다.** 이메일·비밀번호 가입은 만들지 않습니다. 로그인 화면에 휴대폰 인증 UI를 넣지 마세요.

**소비자에게는 본인확인을 요구하지 않습니다.** 로그인·예약·결제 어디에도 넣지 않습니다. 본인확인은 **공급자 등록에만** 있습니다(15-1). 결제 시 사용자가 겪는 인증은 카드사 인증이고 PG가 알아서 처리합니다. "문자인증"이나 "결제 시 본인확인"이라는 표현이 옛 문서에 남아 있으면 폐기된 설계입니다.

**아동 안전은 예약 폼으로 확보합니다.** 참가자 이름·연령, 보호자 연락처, 비상 연락처, 특이사항을 `bookings.participants`/`guardian`/`emergencyPhone`에 받습니다. 서버에서 인원수·대상연령 범위를 검증합니다(15-6).

**실명·CI 같은 본인확인 값은 `users` 본문에 저장하지 않습니다.** `users/{uid}/private/identity` 하위 문서에 넣고, CI는 화면에 절대 내려보내지 않습니다. 중복 가입 판별은 서버에서만 합니다.

**연락처는 출처로 가릅니다 — 소셜이 준 번호는 마이페이지에서 잠기고, 직접 입력한 번호는 `phoneIndex`를 선점하지 않습니다** (2026-09-09, 스키마 2-14). `users.phoneSource`가 `naver`/`kakao`면 그 서비스가 본인 확인을 거친 값이라 `PATCH /users/me`가 변경을 거부하고, 바꾸는 길은 그 서비스에서 바꾼 뒤 재로그인(소셜 값이 덮음)입니다. `manual`은 인증 안 된 값이라 **선점도 조회도 하지 않고** 본인 안내 발송에만 씁니다 — 그래서 **남이 쓰는 번호를 넣어도 응답이 같습니다.** 「이미 쓰는 번호입니다」처럼 응답을 가르는 분기를 다시 만들지 마세요: 그 응답 하나가 번호를 찍어보는 것만으로 회원 여부를 알아내는 구멍(8/28 B-1)이었습니다. 보안규칙도 `phone`·`phoneSource`의 클라이언트 직접 쓰기를 막습니다.

**프로그램 게시 심사가 없어진 뒤에도 게시 상태 전환은 서버만 합니다** (2026-09-09, ⑨). 보안규칙상 소유자는 `status`를 직접 못 쓰고, 게시는 `POST /programs/{id}/publish`, 내림·숨김·재게시 승인은 각자의 서버 경로를 거칩니다 — 「심사가 없다」는 것은 사람의 승인이 없다는 뜻이고 서버 검증(회차·제목·자격 승인)이 없다는 뜻이 아닙니다. 관리자 숨기기·승인·반려는 `reviewedBy/At`·`reviewNote`로 누가 언제 했는지 남기고, 변경 기록(`programs/{id}/history`)은 **클라이언트가 쓸 수 없습니다** — 쓸 수 있으면 기록을 지우거나 위조해 사후 검수가 성립하지 않습니다.

**보안규칙을 고치면 테스트를 함께 고칩니다.** 규칙은 눈으로 봐서 맞는지 알 수 없습니다 — 실제로 v9까지의 규칙에 권한 상승 취약점이 있었고 리뷰로는 못 잡았습니다. 스키마 6-3의 케이스 22종을 에뮬레이터로 돌립니다.

## 법령 대응 — 관리자 계정 2차 인증 (2026-09-02 신설 · 아직 안 만들었습니다)

**오픈 전에 관리자 계정에 2차 인증을 붙여야 합니다.** 근거는 「개인정보의 안전성 확보조치 기준」의 접근통제 조항입니다 — 개인정보를 다루는 사람이 **인터넷을 통해 외부에서** 개인정보처리시스템에 접속할 때는 인증서·일회용 비밀번호 같은 **안전한 인증수단**을 적용해야 합니다. `/admin`은 회원 이름·연락처·예약자 정보를 다루고 사무실이 아닌 곳에서 접속하므로 이 조항의 대상입니다.

**손님 로그인에는 넣지 마세요.** 이 조항은 「접근 권한을 가진 취급자」에게 적용되고 **정보주체(손님 본인)는 명시적으로 제외**됩니다. 카카오·네이버 로그인에 2차 인증을 더하면 가입 이탈만 늘고 근거도 없습니다.

**⚠️ 파이어베이스 기본 다중 인증(MFA)을 그대로 쓰지 못할 가능성이 큽니다.** 우리는 소셜 로그인 뒤 **서버가 발급한 Custom Token**으로 로그인하는데(15-7), Firebase MFA는 이 경로를 지원하지 않습니다. **직접 만들어야 할 확률이 높으니 일정을 그만큼 잡으세요** — 「설정 한 줄」로 끝나는 작업이 아닙니다.

**방통위 「대량문자 전송자격인증제」는 우리 대상이 아닙니다** (2026-09-02 확인). 그 제도는 **문자를 대량으로 파는 사업자**(문자재판매사업자)가 문자중계사업자에게서 받는 인증이고, 심사 항목에 있는 2차 인증도 **그 사업자의 발송 시스템** 이야기입니다. 우리는 사서 쓰는 쪽이고, 보낼 문자도 예약 확정·일정 변경 같은 **정보성 안내**라 제도가 겨냥하는 「영리 목적의 광고성 대량 문자」에 해당하지 않습니다.

> **홍보 문자를 보내기 시작하면 이 판단이 뒤집힙니다.** 팀 방침은 **보내지 않는 것**입니다(2026-09-02 확인). 방침이 바뀌면 마케팅 수신 동의(2-12, 미구현)부터 필요합니다.
>
> **문자 대행사와 계약할 때 「이용 기업에도 요구되는 조치가 있는지」를 직접 물어보세요.** 대행사는 인증을 받으면서 이미 다 겪어봤으므로 우리가 무엇을 해야 하는지 가장 정확히 압니다. 규정은 해석 여지가 있어 우리끼리 판단하는 것보다 확실합니다.

## 날아가면 어떻게 되나 — 복구 수단과 남은 구멍 (2026-09-11 신설)

| 무엇이 날아가면 | 지금 대처 | 상태 |

### 되살리는 방법

- **되돌리기(PITR)** — 잘못 지운 것을 알아차린 시점에서 **7일 안**이면, 콘솔 또는 `gcloud firestore databases restore`로 그 시각의 상태를 **새 데이터베이스로** 만들어 확인한 뒤 필요한 문서만 옮깁니다. 원본을 그 자리에서 덮지 않습니다 — 덮으면 그 뒤에 들어온 정상 데이터까지 함께 사라집니다
- **자동 백업** — `firebase firestore:backups:list`로 시점을 고르고 `firebase firestore:backups:restore --backup <이름> --database <새이름>`으로 새 데이터베이스에 복원. 마찬가지로 원본을 덮지 않습니다
- **둘 다 새 데이터베이스가 생기므로** 확인이 끝나면 지워야 비용이 안 남습니다(Standard 에디션은 데이터베이스를 여러 개 둘 수 있음)
- **비용** — 되돌리기·백업 모두 저장량에 비례합니다. 지금 데이터가 아주 작아 **월 수십 원 수준**이고, 손님이 쌓여도 백업 비용이 사고 한 번의 비용을 넘는 일은 없습니다
