## 절대 규칙

**돈·권한·상태가 걸린 데이터는 클라이언트가 직접 쓰지 않습니다.**
`bookings` `payments` `settlements` `reviews` `providerProfiles` — 전부 Cloud Functions(Admin SDK) 경유. 보안규칙에서 `allow write: if false`로 막혀 있습니다.

**관리자에게도 클라이언트 쓰기를 열지 않습니다.** (`voucherAds`만 예외)
심사·정산은 반드시 `/admin/*` API를 거칩니다. 감사로그를 남겨야 하기 때문입니다.

**보안규칙은 클라이언트 SDK에만 적용됩니다.** Cloud Functions는 Admin SDK라 규칙을 우회합니다. `/admin/*` 함수는 진입부에서 `context.auth.token.admin`을 직접 검사해야 합니다. 프론트 라우트 가드는 UX 장치일 뿐 보안이 아닙니다.

**결제 금액은 서버가 정합니다.** 클라이언트가 보낸 금액은 무시하고 `bookings.totalAmount`를 씁니다. 웹훅에서 실결제액과 대조하되 **기준은 `bookings.unitPrice`(예약 시점 스냅샷)이지 `programs.price`(현재가)가 아닙니다.**

**`users.role`은 어떤 경로로도 클라이언트가 못 씁니다.** 관리자 지정은 Admin SDK 스크립트로 `users.role`과 Custom Claims(`admin: true`)를 **동시에** 갱신합니다. 하나만 하면 화면이 안 열립니다.

**가입은 소셜 2종(카카오·네이버)뿐입니다.** 이메일·비밀번호 가입은 만들지 않습니다. 로그인 화면에 휴대폰 인증 UI를 넣지 마세요.

**소비자에게는 본인확인을 요구하지 않습니다.** 로그인·예약·결제 어디에도 넣지 않습니다. 본인확인은 **공급자 등록에만** 있습니다(15-1). 결제 시 사용자가 겪는 인증은 카드사 인증이고 PG가 알아서 처리합니다. "문자인증"이나 "결제 시 본인확인"이라는 표현이 옛 문서에 남아 있으면 폐기된 설계입니다.

**아동 안전은 예약 폼으로 확보합니다.** 참가자 이름·연령, 보호자 연락처, 비상 연락처, 특이사항을 `bookings.participants`/`guardian`/`emergencyPhone`에 받습니다. 서버에서 인원수·대상연령 범위를 검증합니다(15-6).

**실명·CI 같은 본인확인 값은 `users` 본문에 저장하지 않습니다.** `users/{uid}/private/identity` 하위 문서에 넣고, CI는 화면에 절대 내려보내지 않습니다. 중복 가입 판별은 서버에서만 합니다.

**보안규칙을 고치면 테스트를 함께 고칩니다.** 규칙은 눈으로 봐서 맞는지 알 수 없습니다 — 실제로 v9까지의 규칙에 권한 상승 취약점이 있었고 리뷰로는 못 잡았습니다. 스키마 6-3의 케이스 22종을 에뮬레이터로 돌립니다.
